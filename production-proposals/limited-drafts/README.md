# 限定下書きスキーマ提案（実行禁止）

前提とされる本番の履歴は0001,0002,0003,0004,0012であり、現時点では確認していない。対象は専用本番D1。拒否済みの本番DB照会は別の根拠なく再試行しない。この2ファイルは明示的な別途レビュー用であり自動migrationの対象に入らない。現在のmigrationsディレクトリを連続適用すると0006〜0011等まで含むため使用しない。

`0005-private-drafts.sql` は既存の同番号の元ファイルと完全一致し、本人に紐づく非公開下書き表とインデックスのみを追加する。`limited-draft-grants.sql` は最大1件の許可表のみを追加し、レコードは作らない。ledgerにどう記録するか、別途空き番号や部分履歴との整合を確認するまでは未決定。既存テーブル・値・migration ledgerを変更するSQLは含まない。前提schemaの欠落、衝突、部分適用、結果不明は停止して調査し、無条件の再実行やIF NOT EXISTSで隠さない。

本提案は初期operator、在籍審査、pendingからactiveへの状態変更、grant行の作成を含まない。新しいローカル設計は指定pending本人の下書き試験に限定し、activeの在籍承認とは区別する。既存AdmissionStoreは独立したactive operatorと本人以外の判断を必要とし、初期信頼連鎖は未解決。学校メールや申請受付を在籍承認とみなさない。実際の申請者pending/epoch0は依頼情報であり、この作業では実DBの行を照会していない。許可と取消には別途対象・実行主体・認可・監査と結果確認を定める。

ローカルのみの `python3 production-proposals/limited-drafts/rehearse.py` は架空データ・メモリ上のSQLiteで前提schemaと提案SQLを適用し、サンプル、pending/epoch0、ledgerの保全・1人上限・期限・取消による最終SQL拒否を検証する。本番D1、実ID、operator、認証情報は使用せず、D1実機の時刻や同時実行の証明ではない。

限定grantは対象pending account ID・epoch・期限を拘束し、DBの取消状態と実行時刻をセッション発行・照会・下書き最終SQLで照合する。通常ログインや公開の権限にはならない。再発行は既存sessionの混入とepoch変更を考慮し別途設計する。本SQL提案に本人の状態変更やgrant行投入は含めない。

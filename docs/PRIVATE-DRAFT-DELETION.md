# 本人限定下書きの削除

## 仮説と範囲

試用で保存した文章を本人が片付けられれば、知識・経験を書き残す試用を安心して行える。PRDの執筆・下書き再開を支える仮説であり、学生による需要・価値の検証結果ではない。

既存の `privateOnly` 下書き画面にだけ削除操作を追加する。通常のローカル公開エディタには表示しない。下書きの削除と、公開記事の公開停止・削除は別の操作である。既存の DELETE API、CSRF、所有者・保存版・セッション・試用grantの最終SQL条件を変更しない。

## 動作と受入条件

- 開いている下書きの保存タイトル・版と、未保存の変更も失われることを確認してから明示削除する。キャンセルではDELETEを送らない。確認は既存の非表示・inert境界の内側に置き、別のDOMへportalしない。
- DELETEは確認した保存版の `expectedVersion` と既存のpurpose-bound CSRFを送る。正確な200 JSON `{deleted:true}` を検証した後だけ、対象の一覧・編集・比較・プレビュー・未保存状態を消す。他の下書きは保持する。
- 競合、通信失敗、期限切れ、不正な応答を削除成功と扱わない。変更結果は自動再送しない。結果不明時は手元の文章を保持し、保存・再削除を止める。保存版を再取得し、明示的にその版を基準にしてから操作をやり直す。新しい保存版の削除には新しい確認が必要。
- 一覧は最新20件であり、一覧から消えたことは削除成功の証拠にならない。読取の404も削除済み・取得不能を区別しない。保存版を確認できなければ、成功と断定せず手元の文章を残す。
- セッション変更・失効時は既存のguardで旧編集画面を閉じる。通信不明時の非表示・同一セッション再確認も従来どおり。通信の中止は確定済みの削除を取り消さない。

## 期限後の残条件

自己削除は有効な試用grantとセッションがある間だけ利用できる。試用期限後・取消後は編集と同様に削除も拒否する。期限による自動削除は実装していない。UI追加のために期限・権限を延長したり、認可を緩めたりしない。

期限後の削除を保証するには、実際の保持期限・対象を決めた運用削除、または本人確認を伴う削除専用の経路が必要。バックアップ・ログを含む消去保証は別途確認が必要で、今回のDB行削除やブラウザ試験では証明しない。実データを削除する運用はこの変更では実行していない。

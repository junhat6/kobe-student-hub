# Independent QA — lazy article-body recovery

Date: 2026-11-03. Reviewer: independent QA agent in a separate task/context from implementation. Scope: [Issue #13](https://github.com/junhat6/kobe-student-hub/issues/13), tested implementation commit `96caaefc08d886c7b3bb4940045fbd9648257dc0` ([PR #14](https://github.com/junhat6/kobe-student-hub/pull/14)).

## Source review

No blocking finding in the scoped change.

The new error boundary surrounds only the lazy Markdown body renderer. An import/render failure replaces the body with an explicit alert, a full-page reload action and an article-discovery link. The title, reader context, author/related navigation and surrounding app remain outside that boundary. It does not display an internal exception, raw request or authentication data.

The retry action uses a real page reload. It does not pretend that remounting React.lazy clears a previously rejected module promise. The article-keyed boundary may reset when navigating, but the failed lazy import remains failed until reload; the test deliberately checks failure again after returning through the list, then verifies successful reload after removing the injected failure.

No authentication, contract, cloud configuration, database schema or remote SQL change is in this UI recovery patch. The behavior is for the current read-only sample preview, not editor/draft recovery or complete offline support.

## Independent execution

After the implementer confirmed its shared build/full-test run was finished, this reviewer independently ran the focused failure-injection test in both configured browser projects:

```text
npx playwright test tests/body-recovery.spec.ts --workers=2 --output=test-results-independent-body --reporter=list

✓ [mobile]  failed body chunk preserves navigation and recovers after reload
✓ [desktop] failed body chunk preserves navigation and recovers after reload
2 passed (3.4s)
```

Required sandbox escalation allowed local Chromium and localhost runtime access. This run used the final prepared local build; it did not deploy or probe failures on the public preview. Desktop is Chromium desktop emulation. Mobile is Chromium with iPhone 13 device settings, not a physical iPhone or Safari run.

The independently executed sequence:

1. Intercepted only `MarkdownRenderer-*.js` with HTTP 503; catalog/page data remained available.
2. Opened the Git article and observed the body-unavailable heading, while article title and reader context stayed visible.
3. Asserted no horizontal page overflow and captured the failure view.
4. Used `ほかの記事を探す` to return to the working list, reopened the article and observed the limited failure alert again.
5. Removed the chunk interception, pressed `ページを再読み込み`, and verified the body/code block appeared and failure heading disappeared.
6. Captured the recovered view.

This is a specific lazy-JavaScript-chunk failure/recovery check. It is not a complete offline, cache-version, permanent-404, every-render-exception, screen-reader or real-network reliability audit. The implementer's 59 unit/Worker tests and 20 full E2E results are separate evidence; this reviewer independently reran only the two focused browser cases above.

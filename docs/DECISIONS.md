## 2026-11-22 — アプリ全体の UI を、学生が普段使うメジャーなサービスの型の「キメラ」にする（オーナーの考えを受けた方針）

オーナー（服部）の考え：プロフィール系を GitHub などのキメラにする見直しと同じ理由（利用者が普段使うメジャーなサービスの型なら、使い方を既に知っていて認知負荷が低い）が当てはまるところは、プロフィールに限らずアプリ全体でキメラにしたい。どこに当てはまるかの判断は任せる。独自 UI を新しく作る前に、学生が普段使うメジャーなサービスに既にある型で済まないかを先に検討してほしい。これを受けて次のように決める。

1. **UI/UX の原則にする。** [ux-rubric.md](loop/ux-rubric.md#情報設計の原則オーナー方針-2026-11-22) の情報設計の原則に7「独自の型を作る前に、メジャーなサービスの型を探す」を足し、AGENTS.md の UI の決まり・polish の見る手順・patrol の観点3（型）から参照する。「文字は少なく」（原則1・3）の近道として位置づける：知っている型なら説明文が要らない。
2. **当てはめの判断は「同じ役目の画面が、学生が毎日使うサービスにあるか」。** あれば置き場所・アイコン・操作の順番をその型に寄せ、部分ごとに別のサービスから借りてよい。2026-11-22 時点の当てはめは ux-rubric の「見比べる型」の表（ヘッダー＝note/Zenn、記事の操作＝note/Zenn/Qiita、通報＝X/YouTube の「…」、エディタ＝Zenn/note、閲覧履歴＝YouTube/Chrome、検索＝YouTube/Zenn、公開停止＝YouTube Studio/note など）。表に無い画面は、作る前に型を探して表に足す。
3. **借りるのは形で、決まりは借りない。** 恒久条件（学校Googleの本人確認、閲覧履歴は本人専用、学校メール・申告年度は非公開、通報の運営、公開DTO）は借り先のサービスに合わせて緩めない。例：YouTube の履歴の型を借りても、履歴は本人以外に見せない。
4. **目的に反する仕組みは、メジャーでも借りない。** フォロー／フォロワー数、ランキング、DM、閲覧数の公開、通知で連続をせかすこと。友だち探しアプリにしない・記事と作品が主役、という目的と、同日の「続けたくなる体験」5 に反するため。
5. **出し方。** 型の見直しはループの通常の仕事として進める（polish が R0/R1 を直し、R2 や大きい組み替えは `loop:ux` Issue）。既存の Issue と重なるもの（#203 公開停止、#210 画像、#143 内部用語）はそちらに寄せる先を書き足し、新しく立てない。11-24 の宣伝（#217）より前に、学生が使う流れを大きく組み替えることはしない。宣伝直前に形を変えると、検証していない画面で初めての学生を迎えることになるため。
6. 採らない場合の影響：画面ごとに独自の置き場所と説明文が増え、「文字は少なく」を守るために毎回説明を削っては足す後追いになる。逆に型をそのまま写すと、フォロー数や閲覧数のように目的と恒久条件に反するものまで入る（3・4 で止める）。
7. 仮説 H07：同じ役目の画面をメジャーなサービスの型に寄せると、初めての学生が迷う回数（patrol の S2 件数、実利用者の「どこを押せば」の問い合わせ）が減る。未検証。AI の巡回で S2 が減ることは学生にとっての価値の証拠ではなく、確かめるには宣伝後の実利用者の声と、下書きから公開までに離脱した割合を見る。

## 2026-11-22 — #12 の expand：R2 と D1 の両方に書き、読みは R2→D1、key に sha256 を含める

オーナーが R2 を有効化した（#218）。agent が private bucket `kobe-student-hub-media`（APAC、r2.dev 無効・独自ドメインなし）を作り、本番設定に binding `MEDIA_BUCKET` を足した。

1. **expand の間は両方に書く。** `media_assets.payload` は `NOT NULL` と CHECK 付きで、列の条件を変えるには表の作り直し（contract）が要る。いま D1 に書くのをやめると、1つ前の Worker へ rollback した時に R2 にしか無い画像が読めなくなる。R2 に先に書き、失敗したら D1 の行を作らない。D1 が拒んだら object を消し、取り残しは cron（15分ごと）で D1 に行が無く1時間以上たった object を掃除する。
2. **読み出しの認可は D1 だけ。** D1 で所有者・公開状態を確かめた行の id と sha256 から key を作り、R2 の中身を sha256 で照合してから返す。R2 に無い・合わない時は、同じ認可の SQL を payload 付きでもう一度引く（認可を飛ばす経路を作らない）。
3. **key は `media/<id>/<sha256>`。** id は利用者が決めるので、他人が同じ id で上げても別の key になり、既存の画像を上書きできない。
4. 1つ前の Worker が書いた D1 だけの行は、新しい列 `object_stored_at_ms` が NULL のものを cron が R2 へ写す（0031 は列の追加だけ）。R2 の権限が無い deploy 用 token でも R2 binding 付きの deploy は通ることを使い捨て Worker で確かめた（token への権限追加は不要）。
5. 次（contract）：本番でこの版が動き、全行の `object_stored_at_ms` が埋まったら、payload を書かない版と、payload を任意にする表の作り直しを別の列車で出す。#188・#195 の容量上限はその後に R2 の容量で決め直す。プロフィール画像（`profile_avatars`、1枚 64 KiB）は D1 のまま（容量の頭打ちに効かないため）。
6. 採らない場合の影響：R2 だけに書く形にすると rollback で画像が欠け、key に sha256 を入れないと id を使い回した上書きで他人の画像を差し替えられる。

## 2026-11-22 — 続けたくなる体験：積み上がりが見え、届いた手応えがあり、出した瞬間が楽しい（オーナーの考えを受けた方針）

オーナー（服部）の考え：継続して使うと達成感があり、「これからも使いたい」と思える体験にしたい。アプリをポップにして楽しくする方向のアプリもあり、そういう感じで使い続けたくなる体験に寄せたい。プロフィールの「草」もこの継続の達成感の一部として位置づける。具体的な仕掛けの設計は agent に任せる。これを受けて次のように決める。

1. **達成感の源は3つに絞る。** ①自分が出したものが積み上がって見える（草）②誰かに届いた手応え（いいね等を本人に返す）③出した瞬間が楽しい（お祝いの演出）。どれも「記事・作品を出す」という、このサイトの目的に沿う行動にだけ付ける。閲覧・ログイン・いいねを押した回数には付けない（友だち探しや滞在時間を競うアプリにしない、という目的に反するため）。
2. **草は公開の事実だけで作る。** 公開中の記事の公開・公開版の更新と、公開中の作品の公開を、日本時間の日ごとに数える（`GET /api/students/:id/activity`、直近26週）。下書き・閲覧履歴・いいね・停止した記事は数えない（非公開データを公開面に出さない／停止した記事の痕跡を残さない）。日付は日単位までで時刻は出さない。公開プロフィールの既存 DTO には足さず別の読み取り口にした（古いクライアントの厳密な検証を壊さず、草の失敗でプロフィールが読めなくならないように）。
3. **連続は「週」で数える。** 日単位の連続（ストリーク）は採らない。試験・課題・バイトで1日空くと切れ、続けた人への罰になるため。今週がまだ終わっていなければ連続は切れていない扱いにし、マイページでだけ「今週も出すと n 週連続」と次の一歩を示す。
4. **見せ方はポップに、でも読みやすさは崩さない。** 草は緑の4段階、連続週は暖色（`--warm`）のチップ、マスが順に芽吹く小さな動き。公開した瞬間に紙吹雪と「+1」の芽を約2秒出す（記事・作品とも、普通の面だけ）。演出はすべて装飾で、結果は従来どおり状態文が伝える。`prefers-reduced-motion` では出さない。文字は増やさず、数はアイコン＋数字で示す（UI の決まり 2026-11-22）。
5. **採らないもの。** ランキング・他人との比較（数を競わせると、記事の中身より本数に寄る）、閲覧数の公開（閲覧履歴は本人専用の恒久条件に反する方向に寄る）、通知でせかす（プッシュ・メールで「連続が切れます」と送らない）、日単位ストリーク（3）。
6. **次に足すもの（Issue で積む）。** 届いた手応え（自分の記事に付いたいいねをマイページで本人に返す）、節目（初公開・5本・4週連続など、マイページだけで見せる）、全体のポップさの見直し（UX 巡回の観点に「楽しさ」を足す）。
7. 採らない場合の影響：出したものが積み上がって見えないと、1本目を出した後に戻ってくる理由がなく、11-24 の宣伝で来た学生が一度きりで終わりやすい。逆に日次ストリークや通知で引き留めると、短期の数字は上がっても、続けられなかった学生が離れる理由になる。
8. 仮説 H06：草と週の連続をプロフィールとマイページで見せると、2本目を公開する学生の割合と、最初の公開から4週以内にもう一度公開する割合が上がる。未検証。確かめ方は本番の公開日の分布（公開の事実だけ）を宣伝後2週・4週で数える。AI の動作確認は学生にとっての価値の証拠ではない。

## 2026-11-22 — オーナーのレビューを蓄積し、次の執筆に活かす（オーナーの考えを受けた方針）

オーナー（服部）の考え：本番の公開記事が0件のまま 11-24 の宣伝を迎えたくない。記事の執筆が実際に回り始めてほしい。オーナーはアプリに投稿された記事をどんどんレビューしていくので、そのレビューでオーナーの好み（どんな記事を良いと感じるか）が蓄積され、次の執筆に活きる土台が欲しい。最初の記事は、オーナーが既に渡した材料（北野川線沿いと三宮のラーメン・ランチの実体験）から作り、アプリ上でレビューできる形にしてほしい。これを受けて次のように決める。

1. **レビューはアプリの中で、運営者だけが残す。** 公開記事のページの下に、運営者（`MODERATION_OPERATOR_ACCOUNT_IDS`）にだけ「良い／ふつう／合わない」（アイコン）、固定の評価項目（体験が具体的・本人の言葉・次の行動になる・写真・図が効く・長さがちょうどいい／中身が薄い・盛っている・長い・誰向けか分からない・時期・値段などが足りない）、ひとこと（500字まで）の欄を出す。保存は D1 `editorial_reviews`（migration 0030、expand のみ、追記だけで履歴を残す）。運営者以外には API ごと 404 で、欄の存在も見えない。R2（非公開データ・運営・migration）なので release flag `EDITORIAL_REVIEW_RELEASE_ENABLED` を閉じたまま main に入れ、別 context の独立検証を経て開ける。
2. **評価項目は固定のコードで持つ。** 自由記述だけだと件数で傾向が言えず、項目だけだと理由が残らないので両方を持つ。項目は足してよいが、コードの改名・使い回しはしない（古いレビューの意味が変わるため）。
3. **蓄積したレビューは「好みの台帳」に蒸留して、全部の執筆経路に渡す。** 台帳は `src/agent/editorial-taste.ts` の `EDITORIAL_TASTE`（抽象的な決まりの行と根拠の件数・日付）。下書き画面の依頼文・MCP の `get_writing_guide`・執筆スキル SKILL.md の3経路が同じ文を持つことをテストで固定する。初版はオーナーが既に言ったこと（本人の言葉のまま・盛らない、行く前に知りたい具体、良し悪しを正直に、写真多め）だけで作り、根拠は「オーナー指示」。
4. **台帳を書き換えるのは新しい editor ループだけ。** `docs/loop/prompts/editor.md`。本番 D1 のレビューを読むだけで読み、AI が作った下書きの原本とオーナーが公開した版の差（消した文・足した文）も同じ重さの材料にする。3件以上で同じ向きのときだけ台帳に1行足す。台帳は公開されるので、ひとことの引用・記事名・書いた人・店名は書かない。生のレビューと材料と原本はこの Mac の `~/.config/kobe-student-hub/` にだけ置く。
5. **材料から下書きを作るのも editor。** 材料は `~/.config/kobe-student-hub/materials/inbox/`（本人の言葉のまま）。中身は材料にある本人の経験だけ（2026-11-22「食事レビュー」の5を引き継ぐ。本人が渡した本人の経験から、本人の下書きを用意するのは「agent がレビュー本文を作る」には当たらないと解する）。下書きは、書き手の MCP 接続（C21、#219）が本番で開いていれば本人の下書きに直接作り、まだなら `~/ksh-drafts/` のファイルを本人が下書き画面で取り込む。本番 D1 に下書きを直接入れることはしない（本人確認・所有者チェックを通らない書き込みになり、AGENTS.md の恒久条件に反する）。
6. **形の比べ方も材料にする。** 同じ材料からまとめ型と1店深掘り型など2本まで作り、どちらが公開されたかで好みを学ぶ。初回は同じ材料からのまとめ型と1店深掘り型、別の材料からの行きつけ型の3本。
7. 採らない場合の影響：レビューを会話や公開 Issue で受けると、次のセッションから見えないか、学生の記事への評価が公開されてしまう。台帳に蒸留せず生のレビューを依頼文に入れると、他の学生の記事への評価が全利用者の AI に渡る。下書きを D1 に直接入れると早いが、本人確認を通らない書き込みの前例になる。
8. 仮説 H05：オーナーのレビューから作った台帳に沿って書いた下書きは、台帳なしの下書きより、オーナーが直す量が減り、公開されやすい。未検証。確かめ方は、原本と公開版の差の量と、2週間以内に公開された割合を editor log の数で追う（オーナーの好みの記録であって、学生にとっての価値の証拠ではない）。

## 2026-11-22 — 過去セッションの秘密は確約せず、免責を示してベストエフォートで伏せる（オーナー決定、C21 条件5・7 の変更）

オーナー（服部）の判断：過去セッションの中身は、そもそも利用者本人の AI エージェント（Claude 等）に渡るもの。本人のエージェントは本人のマシンで本人の権限で動いている前提なので、「秘密を100%伏せられること」をアプリ側が確約する形にこだわらない。代わりに免責をきちんと示す。伏せ字はベストエフォートで続けてよいが、確約できないことを理由に全体を止めない。#214 の blocked もこの判断で解く。完成台帳 C21 の受け入れ条件の変更はオーナー本人の判断として行う（agent による弱体化ではない）。

決めたこと：

1. **受け入れの変更。** C21 条件5（MCP の書き込みと秘密検査）は「規則での秘密検査はベストエフォート。網羅は確約せず合否に含めない」と明記。条件7（/agents・/llms.txt・執筆スキル）は「伏せ字スクリプトを配らない」をやめ、「過去セッションを材料にする手順の手前で免責4点を明示する。伏せ字の補助はベストエフォートとして配ってよく、網羅は合否に含めない」に変える。オーナーの言う「条件5」は秘密の扱いの条件（旧条件5＝キットの伏せ字、それを置き換えた現条件5・7）を指すと解し、両方に当てた。
2. **免責として示す4点**（SKILL.md の手順2の頭、/agents の「作業履歴から書く」、MCP の書き方ガイド、`session_index.py` の `--help` と出力の頭）：①過去セッションを参照すると、その中身が本人の AI エージェント（とその提供元のサービス）に渡る ②セッションにはパスワード・API キー・秘密鍵・メール・他人の情報などが含まれうる ③伏せ字の補助は完全ではなく、すり抜けがある ④参照するかどうか、記事に何を載せるかは本人の責任で決める（公開前に全文を読む）。文は短く、手順の手前に置く（UI の「文字は少なく」の方針は画面の操作の話で、ここは利用者が同意する前提の説明なので省かない）。
3. **前の決定の一部を戻す。** 同日の「MCP＋学校Googleでの接続許可に作り直す」3 の「`session_index.py` は配布をやめる」は取り消し、ベストエフォートの補助として配り続ける。理由：履歴を丸ごと読むより、依頼文と返答の文だけに絞り明らかな秘密を伏せた会話録のほうが、エージェントに渡る量も秘密も減る。完全でなくても、無いより安全側に寄る。同 10（アプリは履歴を受け取らない、届くのは完成した下書きだけ）・11（秘密検査は止めずに知らせる）はそのまま。守る線は引き続き「サイトが受け取るのは完成した下書きだけ」「下書きは非公開」「公開は本人が全文を見て押す」。
4. **#214 の組み直し。** 新しいすり抜けの形を見つけることを不合格の理由にしない。代わりに、ベストエフォートの道具として害のある不具合だけを直す：長いダッシュ・空白で処理時間が入力長の2乗に伸びる（2万字で約18秒）、Markdown の箇条書き「- Begin … private key」で文末まで伏せすぎる、の2点と、上の免責の表示。これまでに伏せられるようになった形（`tests/agent-kit-session-index.test.ts`）は後退させない。見つかったすり抜けは、直せる範囲で足してよい（合否には含めない）。

## 2026-11-22 — Dependabot の PR は人が見ない前提で回す（オーナー決定）

オーナー（服部）の指示：Dependabot は人間が管理する手間をなくすための仕組みなので、PR を人が1件ずつ見る前提にしない。agent がレビュー・影響確認・必要な修正をしてマージまで進め、パッチ更新などは自動マージに寄せる。破壊的で影響が大きいものだけ、無理にマージせず理由と一緒に報告する。

3. major・0.x・health 失敗は garden が人に回さずに片付ける：changelog を読み、使っている箇所を直し、`rc/<sha7>` の full CI を見てマージ（[garden.md](loop/prompts/garden.md) の 4）。
4. マージしないのは、移行に R1 以上の設計変更が要る・本番データや認証の挙動が変わるときだけ。`loop:garden` Issue に理由・影響範囲を書いて報告とする。`needs-human` にはしない（人の判断が要るのは課金・資格情報・実利用者だけ、という 2026-11-21 の線引きのまま）。
5. 採らなかったもの：全更新の自動マージ。major は API が変わり unit test だけでは足りないことが多く、release の full CI で初めて赤になると列車が止まる。main の全 push に必須 CI を掛ける案も、agent の直接 push を止めるので採らない。
6. 残るすき間：GITHUB_TOKEN のマージは main-health を起こさないので、別々に green だった2本が重なって壊れる場合は release の verify で初めて見つかる。cooldown と週1のまとめ（group）で同時に入る本数が少ないため、今は許容する。

## 2026-11-22 — 利用者が自分の AI エージェントで書き・読めるようにする（オーナーの考えを受けた方針）

> 2・4 は同日の「AI エージェントとの接続を MCP＋学校Googleでの接続許可に作り直す」で置き換えた。

オーナー（服部）の考え：利用者はみな AI エージェントのサブスクを持っている。記事をたくさん集めたいので、利用者が自分の AI エージェントで記事を書けるようにしたい。執筆に限らず、利用者の AI エージェントとこのアプリの距離を近くしたい。これを受けて次のように決める。

1. 「書く」はファイルを受け渡しにする。下書き画面の「自分のAIエージェントと書く」で、(a) 記事の形・守ること・いまの下書きを入れた依頼文をコピーし、(b) AI が書いた Markdown ファイル（先頭に title・summary・tags・audience・prerequisite・outcome・minutes）を貼るか選んで、確認してから下書きに反映する。反映は手元の編集で、保存はこれまでの下書き保存だけが行う。概要・タグなどは「公開の準備」で本人が押したときだけ入る。どの AI でも使え、サーバーの書き込み口と資格情報が増えない（R1 にとどまる）。
2. 「AIとの作業履歴を材料にする」は、利用者の端末の中で完結させる。執筆キット（`/agent-kit/ksh-article/SKILL.md` と、Claude Code・Codex・Gemini CLI・Antigravity CLI の履歴を一覧・要約する `session_index.py`）を公開し、利用者のエージェントがそれを読んで、履歴からネタを3〜5個出し、本人に質問してから下書きファイルを作る。このサイトは履歴を受け取らない。スクリプトは秘密らしき文字列・メール・ユーザー名入りのパスを伏せるが、最終確認は本人が行う。
3. 「読む」は記事ページの「AIに渡す」で、公開済みの記事を出典 URL つきの Markdown としてコピーできるようにする。コピーするのは画面に出ている公開 DTO だけ。案内は `/agents`、エージェント向けの入口は `/llms.txt`。
4. 採らなかったもの：個人用トークンや MCP サーバーで、エージェントが直接下書きを保存・公開する API。距離はもっと近くなるが、新しい資格情報の発行・保管・失効と、本人確認なしの書き込み経路が増える（R2、恒久条件「書き込みはサーバーで確認した学校Google本人確認の上で」に関わる）。ファイル方式で書く量が増えるかを見てから、下書きの保存だけに絞った token の設計を別に検討する。採らない場合の影響：毎回の貼り付け・ファイル選択の手間は残る。
5. AI が書いた記事も、内容の責任は書いた本人（利用ルールの「AIを使った執筆もできます」のまま）。依頼文とキットには「本人がやったことだけを書く・作らない」「個人情報と秘密を伏せる」「画像の出どころ」「お店のレビューの決まり」を入れる。
6. 仮説 H04：自分の AI との作業履歴から書き始められると、白紙から書くより記事を書き上げる学生が増える。未検証。最初の確かめ方は、試用（#5）で「キットを使って下書きを1本作れたか・公開まで進んだか」を聞くこと。AI の動作確認はこの検証にならない。

## 2026-11-22 — 公開プロフィールを書く前の当たり前にし、マイページの文字と操作を減らす（オーナーの考えを受けた方針）

オーナー（服部）の考え：「公開プロフィールを作ると記事を公開できます」という案内では弱い。作らないと進めない・作るのが当たり前の体験にしたい。年度の表し方が分かりにくい。「保存状態を確認」「再読み込み」のような意味のない操作は要らない。文字を減らしてアイコンで伝え、説明が要るものは利用者が知らなくてよい形に設計し直したい。これを受けて次のように決める。

1. **公開プロフィールが無いうちは書けない（画面の形で示す）。** マイページは「プロフィールをつくる」だけの画面になり、記事・作品の画面は「まずプロフィールをつくろう」と作る場所への1ボタンだけを出す。サーバーの書き込み条件は変えない（下書きの保存は API 上は今までどおり可能。画面の順番の決まり）。卒業・入学前で新規投稿できない学生は、プロフィールが無くても下書きの削除・公開停止・在学期間の訂正を続けられる（片付けの道を塞がない）。
2. **プロフィール作成の確認チェックボックスを外す。** 入力欄の上に「公開される見え方」そのもの（カード）を出し、公開を示す地球のアイコンと「公開する」ボタンで、何が誰に見えるかを操作の形で伝える。API の `confirmPublic: true` は従来どおり送る（ボタンを押すこと自体が確認）。Google の氏名・写真を自動で入れないことは変えない。
3. **年度は「2025年4月 → 2027年3月」と選ぶ。** 保存する値（入学年度・卒業予定年度）とサーバーの検証は変えず、画面だけを月の表示の選択にする。入学を選ぶと2年制を仮定して卒業予定を入れる（神戸電子の多くの学科が2年制のため。違えば選び直す）。範囲外の値や逆順は選べないので、入力エラーの説明文が要らなくなる。
4. **確認ボタンを置かず、画面が自分で読み直す。** 保存の結果が分からないとき（応答が失われたとき）は、自動で再送はせず、画面がサーバーの状態を読み直して結果を出す。失敗のときだけ「もう一度」を出す。
5. **アバター画像は次の段階。** 公開される利用者の画像が増えるため、恒久条件の「通報の運営が揃った上で書き込む」に合わせて、プロフィールへの通報と運営の非表示の道を先に用意してから入れる（#198）。それまでは表示名の頭文字のアバターを使う。

採らなかった案：(a) サーバーで「プロフィールが無い人は下書き保存も不可」にする — 既存の下書きを持つ人の片付けを塞ぎ、R2 の権限変更になる割に、画面の順番で十分に「当たり前」を作れる。(b) 卒業予定を「年数（2年制・3年制）」で選ばせる — 留年・転科で実際の卒業月とずれると、結局「何年度か」を考えさせることになる。

## 2026-11-22 — 記事は画像を多く入れて出す（オーナーの考えを受けた方針）

オーナー（服部）の考え：記事には画像をたくさん入れて出してほしい。記事の見た目と読み応えのために、画像の量を重視する。これを受けて次のように決める。

1. 記事の画像は「多いほうがよい」を基本にする。書き方の案内と、利用者の AI エージェントに渡す執筆の依頼文に「見出しごとに1枚以上」を目安として入れる。
2. 1下書き8枚・全体64 MiB の上限は、この方針に足りない。上限を上げる（#195、R2 の migration と独立検証を経る）。上がるまでは、8枚の中で写真と図版を組み合わせる。
3. 画像の出どころは2つに限る。(a) 書く本人が撮った写真・作ったもの。(b) 中身を図にした自作の図版（比べ方・選び方・手順など）。店の公式写真、グルメサイト・地図サービスの写真、検索で見つけた画像は使わない。他人の著作物であり、このサイトは公開されているため。
4. AI 生成の写真風の画像で、実在の店・料理を「その店のもの」に見せない。読者が実物と取り違えるため。図版・イラストだと分かるものは使ってよい。図版には「図：記事用に作成」のように出どころを添える。
5. 写真には、店員・ほかの客が特定できる形で写り込まないようにする。撮影禁止の店では撮らない（レビューの決まり4と同じ）。
6. 仮説 H03：画像の多い記事は、少ない記事より最後まで読まれ、次の行動（店に行く・作品を見る）につながる。未検証。最初の確かめ方は、試用（#5）で、同じ内容の画像あり・なしの記事を見せて比べること。

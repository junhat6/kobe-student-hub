## 2026-11-23 — 記事での外部の文章・画像の引用（オーナーの考えを受けた方針）

オーナー（服部）の考え：記事にネットの画像や口コミを引用してもよい。Muse（ヨッチ）がオーナーに伝えた線引き：口コミなどの文章は、出典を明記し、自分の感想が主・引用が従の最小限なら問題ない。画像は他人の写真をそのまま転載（再アップロード）すると著作権のリスクが高いので、自前の写真を基本にし、外部の画像は公式 SNS の埋め込みやリンクなど権利的に安全な形に限る。この線引きを前提に次のように決める。2026-11-22「記事は画像を多く入れて出す」の3は、アップロードする画像についての決まりとして残す。

1. **文章の引用は認める。条件は4つ。** (a) 本人の経験・感想が主で、引用は必要な部分だけ短く。(b) `>` の引用ブロックで本文と分け、原文のまま写す（言い換え・つなぎ合わせ・作った口コミにしない）。(c) すぐ下に出典（サイト名と URL）を書く。(d) 口コミの投稿者の名前・アカウント名は書かない。理由：(a)〜(c) は著作権法32条の引用として扱われるための一般的な要件（主従・明瞭な区別・出所の明示）に合わせたもの。(d) は恒久条件の「本人以外の名前・アカウント名を出さない」と揃えるため（出典はページの URL で足りる）。法的助言を受けた線引きではなく、一般的な公開サイトの慣行の範囲。
2. **他の人の写真・画像はアップロードし直さない。リンクで紹介する。** 店の公式写真・グルメサイトや地図サービスの写真・SNS の投稿は、保存して下書きに上げず、公式の SNS やページへのリンクにする。アプリ側はもともと外部の画像を表示しない（本文の画像は `/api/media/` のものだけを描き、CSP の `img-src` も自分のサイトだけ）ので、外部の画像を記事に出す道は「再アップロード」しかなく、そこを決まりで止める。
3. **埋め込みは YouTube だけのまま。X・Instagram などの SNS 埋め込みはいまは作らない。** YouTube は URL だけの行が `youtube-nocookie.com` の埋め込みになる（既存）。SNS の埋め込みは提供元のスクリプトを読者のブラウザで動かすため、読者の閲覧が第三者に渡り、CSP と security headers（恒久条件）を広げることになる。リンクでオーナーの「外部の画像を見せたい」はおおむね満たせるので、埋め込みは記事にリンクが積み上がって要望が見えてから、privacy の設計と合わせて考える。採らない場合の影響（いま作った場合）：読者全員の閲覧記録が SNS 提供元に送られ、`script-src 'self'` を崩す。
4. **AI エージェントが書くときは、口コミを作らない。** 本人が渡したもの・エージェントが開いて確かめたものを原文のまま写す。覚えている内容や要約を引用の形で書かない（実在の人の言葉に見えるため）。
5. 決まりの置き場所は1つ：`src/agent/article-format.ts` の `QUOTE_RULES`。執筆の依頼文・MCP の `get_writing_guide`・執筆スキル（`public/agent-kit/ksh-article/SKILL.md`）・下書き画面の「お店のレビューを書くとき」に同じ文で出し、`tests/agent-article-format.test.ts` で揃っていることを確かめる。利用ルール（`/guide#rules`）にも1行足す。
6. 運営での扱い：引用の決まりに合わない記事（出典のない転載・引用が主の記事・他人の写真の再アップロード）は、既存の記事の通報（理由は自由記述。3件で一時非表示）で受け、運営画面で削除か戻すかを決める。権利者からの申し出は問い合わせ窓口で受け、確かめられれば同じく削除する。新しい仕組みは足さない。運営が自分から記事を非表示にする道は今は無いので、通報の届かない違反が見つかったら、そのとき作る。

## 2026-11-23 — お店の記事は1店1本にし、まとめ記事を店ごとに分け直す（オーナーの考えを受けた方針）

オーナー（服部）の考え：記事は店舗ごとに1本ずつ書く形がよい。複数店をまとめた記事より、店ごとの記事のほうが良さそうだという本人の感覚。既存のまとめ下書きも店ごとに分け直してほしい。これを受けて次のように決める。2026-11-22「オーナーのレビューを蓄積し、次の執筆に活かす」の 6（同じ材料からまとめ型と1店深掘り型を作って比べる）は、お店の記事についてはこれで置き換える。

1. **お店の記事は1本に1店。** 好みの台帳 `EDITORIAL_TASTE` に「オーナー指示 2026-11-23」の行として足し、下書き画面・MCP・執筆スキルの全経路に渡す。editor は材料に何軒あっても店ごとに下書きを作る。理由：検索・タグ・関連記事・店に行った後の読み返しが、記事の単位と店の単位が一致しているほど効く。採らない影響：まとめ記事の中の1店を探すには本文を読むしかなく、店ごとの積み上げ（2026-11-22「北野川線沿い」の 3 の「公開済みのレビュー3件」）も数えにくい。
2. **まとめ下書き2本は店ごとに分け直す。** 中身は材料にある本人の言葉だけで、分けて薄くなった店も足さずに「（ここに〇〇を書く）」で空ける。分けた後のまとめ下書きは、本人の非公開の下書き一覧から消す（原本は editor の非公開の置き場所に「分割済み」として残し、「公開されなかった」の材料には数えない）。
3. **届いた写真は、写っている店の記事の素材にする。** 取り込み時にその店の下書きへアップロードする（画像はアプリが描き直してメタデータを落とす）。
4. 比べ方：まとめ型と1店型の比較はやめるが、同じ店について形を変えた2本までは引き続き作ってよい。
5. 仮説 H07：1店1本の記事は、まとめ記事より、読んだ学生がその店に行く・保存する割合が高い。未検証。オーナーの感覚であって学生にとっての価値の証拠ではない。確かめ方は、公開後の店ごとの記事の閲覧から保存・いいねまでの割合を、宣伝後2週で見る。

## 2026-11-23 — 実利用者に関わる運営を agent に任せ、MCP では初めての公開をさせない（オーナー決定）

オーナー（服部）の決定：(1) 実利用者に関わること（通報への対応、アカウントへの措置、利用規約・プライバシーポリシー・免責事項の改定など）も agent が判断・実行してよい。本人が対応するのは手間だから。R3 から外す。免責事項は広く取る（広く書いておき、変更の必要があまり生じない形）。(2) 実利用者のデータは積極的に使ってよい。ただし公開は厳禁で、公開 Issue・公開リポジトリに載せない工夫（置き場所・伏せ方）を必ず伴わせる。(3) 「公開」の境界：みんなに配る MCP 経由では記事を公開できないようにする。記事の初めての公開は人間だけが行う。すでに公開済みの記事は、公開状態のまま編集してよい。これを受けて次のように決める。

1. **R3 は課金・契約だけになる。** 通報への対応・アカウントへの措置・規約類の改定・アプリ内の告知は R2（境界）として agent が行う。決まりの正本は [LOOPS.md](loop/LOOPS.md#実利用者に関わる運営)。措置は戻せるもの（公開停止・利用の制限）を先に選び、理由は非公開の置き場所に残す。理由：運営の判断を人の在席で待つと、通報が放置される時間がそのまま利用者の害になる。採らない影響：通報が積まれたまま、ループの速度がオーナーの応答で決まる。
2. **学外の窓口（SNS・メール・学校への連絡）で実在の学生へ告知・募集することは、agent に使えるアカウントがないので `needs-human` に止まった場所を書く。** 判断は agent がしてよく、権限が無いことだけが理由。
3. **実利用者のデータは「リポジトリの外に置き、公開物には集計と記号だけ」を守って使う。** 置き場所は `~/ksh-private/`（リポジトリの外、git 管理しない）と scratchpad。公開 Issue・commit・PR・CI artifact・`look:review` に、メール・認証 ID・表示名・本文の引用・ログイン後の画面を出さない。個別のことを公開側で指すときは `~/ksh-private/` の記録番号だけを書く。詳細は [LOOPS.md](loop/LOOPS.md#実利用者のデータ)。恒久条件「非公開の利用者フィードバックを公開 Issue に書かない」はそのまま。
4. **MCP には初めての公開の手段を置かない。** `article_publications` に行を作るのはアプリの「公開の準備」（本人のブラウザのセッション・`confirmPublic`）だけ。MCP の書き込みは本人の下書きと、すでに公開済みの記事の改稿（`update_published_article`）に限る。理由：配る MCP は、利用者のエージェントが本人の目を通さずに動く経路。初めての公開は「何を世に出すか」を本人が全文を見て決める唯一の場面なので、人に残す。採らない影響：定時実行のエージェントが、本人が読んでいない記事を公開できてしまう。
5. **公開済みの記事は、MCP から公開したまま直せる（`update_published_article`）。** 下書きの更新と次の改稿の公開を1つのトランザクションで行う（`article_revision_guard` の検査で失敗すれば全体が戻る）。概要・タグなどの公開情報は今の改稿から引き継ぐ。次の場合は受け付けない：まだ公開していない下書き、本人が公開後に直した未公開の変更がある（エージェントが本人の書きかけを公開しないため）、公開停止中・通報の確認中、版が違う、秘密らしき形がある（下書きと違って公開ページに出るので、注意ではなく拒否）。同意画面・/agents・接続一覧・MCP の案内・SKILL.md の「できること」を合わせて直した。MCP はまだ release flag（`AGENT_MCP_RELEASE_ENABLED=false`）で閉じているので、既存の利用者の同意の範囲は変わらない。
6. **免責事項を広げた（`/guide#disclaimer`）。** 接続した AI エージェントの操作は本人の操作として扱う、運営は事前の通知なく公開停止・利用の制限をとりうる、運営の作業の一部に AI を使う、損害の免責の対象に措置・データの消失・AI による処理を含める。「法令上責任を負う場合を除き」の限定は残す（2026-11-22 の項の理由のまま）。データの利用目的として「非公開の情報を含むデータを、提供・改善・安全の確保のために確認・分析することがある（外部の AI サービスでの処理を含む）。本人の同意なく公開しない」を「公開する情報・自分だけの情報」に足した。
7. 変えた文書：AGENTS.md、docs/loop/README.md（原則6・リスク段階）、docs/loop/LOOPS.md（ラベル・本番での禁止・人の待ち行列・実利用者に関わる運営・実利用者のデータ）、docs/loop/ORCA-BOTS-PHILOSOPHY.md、docs/RELEASE.md、release skill、completion.json C21 条件4・5。
8. 変えないもの：いいね・通報を agent が利用者として行わない。実利用者のアカウントでログインしない・資格情報を作らない。初めての公開をオーナーのアカウントで agent が代わりに押すこともしない（境界の趣旨が「初めての公開は人」なので、MCP 以外の経路でも同じ）。
9. 区別：この変更は R2。`update_published_article` は別 context の独立検証を経てから MCP の release flag を開ける（C21 / #219 の検証に含める）。

## 2026-11-23 — 資格情報の発行を条件つきで agent に任せる（オーナー決定）

オーナー（服部）の決定：これまで R3（人の判断）だった「資格情報の発行」を、条件つきでエージェントが判断・実行してよい。条件は (1) スコープを最小限にする（対象リソースと権限を用途に絞り、期限を付けられるものは期限付きにする）、(2) 発行した事実と目的・スコープを記録に残す、(3) 値そのものはログ・ファイル・コマンド・出力に出さない（従来の恒久条件どおり）。これを受けて次のように決める。

1. **資格情報の発行は R3 から外し、R2（境界）として扱う。** R3 に残るのは課金・契約と実利用者への告知・募集・試用だけ。発行の決まり（最小スコープ・期限・置き場所・記録・値を出さない）の正本は [LOOPS.md](loop/LOOPS.md#資格情報の発行)。理由：発行のたびにオーナーの在席を待つと、#166 の migration と同じくループの速度が人の応答で決まる。一方で資格情報は漏れると戻せない境界なので、R0/R1 のように「出して巡回で拾う」扱いにはしない。
2. **記録は下の発行記録に1行ずつ足す。** 発行・入れ替え・取り消しのたびに書く。公開リポジトリなので、account ID・宛先・値は書かず、種類・名前・目的・権限・期限・置き場所の名前・取り消し方だけを書く。理由：後から「どの鍵が何のために生きているか」を1か所で見て、要らない鍵を取り消せるようにする。採らない影響：発行が増えるほど棚卸しができなくなり、漏れたときに範囲が分からない。
3. **値が出力に出る手段しかない場合は発行しない。** 発行の応答はパイプで置き場所へ直接流す。管理画面に1回だけ表示される・ツールの応答に値が返るなど、agent の出力（会話・ログ）を通らずに済まない手段しかないときは、止まった場所を `needs-human` に書いて他を進める。
4. **本番の巡回の「AI エージェント接続の許可（MCP のトークン発行）」も、この決まりで行ってよい。** 同日の項「本番の巡回でログインしてよい」の2の禁止をこの項で置き換える。確かめ終えたら許可を取り消し、発行記録に発行と取り消しを書く。
5. 変えた文書：AGENTS.md、docs/loop/README.md（原則6・リスク段階）、docs/loop/LOOPS.md（本番での禁止・人の待ち行列・資格情報の発行）、docs/RELEASE.md、release skill、docs/loop/ORCA-BOTS-PHILOSOPHY.md。
6. 変えないもの：恒久条件「トークンをファイル・コマンド・出力に置かない」「ログに秘密を出さない」。実利用者の資格情報を作る・代わりに発行することはしない。課金を伴う発行は R3 のまま。

## 2026-11-23 — 好みの台帳はアプリ側に置き、抽象化は利用者のエージェントが行う。オーナーは台帳を改善と自分の記事に使う（オーナー決定、C22 を補い C23 を足す）

オーナー（服部）の決定と方向性：(1) 好みの台帳はアプリ側に置く。生の材料（レビューのひとこと・履歴）は動かさず、抽象化された決まりの行だけをアプリ側に貯める今の設計でよい。(2) アプリ側に AI を持たせない制約どおり、抽象化は利用者側の AI サブスクのエージェントが行う。オーナーは現行の editor ループ（オーナーのエージェント）。一般の利用者は、本人のエージェントが MCP 経由で自分のレビューや下書きと公開版の差を読み、抽象化した行を書き戻す。(3) 貯まった好みを、オーナー自身が機能改善と自分の記事の質向上に使いたい。これを受けて次のように決める。

1. **台帳は2層にする。** 運営の台帳＝`src/agent/editorial-taste.ts` の `EDITORIAL_TASTE`（全員の執筆経路に渡る・公開・書くのは editor ループ＝オーナーのエージェントが commit で）。本人の台帳＝D1 の本人専用の行（その人のエージェントにだけ渡る・非公開・書くのは本人のエージェントが MCP で）。理由：運営の台帳は全利用者の AI に渡るので、変更を git の履歴とテスト（3経路の一致）で追えるほうがよい。本人の台帳は本人の非公開データなので、下書きと同じくサーバーで本人確認・所有者チェックを通した書き込みにする。採らない影響（1層に寄せる）：コードに寄せると一般の利用者が書けず、D1 に寄せると全員に渡る文が履歴とテストの外で変わる。
2. **アプリは抽象化しない。** サーバーがするのは、材料を本人に返す・行を型と上限で受けて保存する・規則での秘密検査（注意だけ、2026-11-22 の追補11と同じ）まで。「行が抽象的か」をサーバーは判定できないので、受け入れの合否は形（1行200字・40行まで・根拠と日付つき・改行と制御文字なし）で見る。本人の台帳は本人にしか渡らないため、抽象化しきれていない行が残っても漏れる先は本人自身に留まる。
3. **材料は MCP で本人のものだけを返す。** ①本人が書いたレビュー（いまは運営者だけが書ける。一般の利用者には空）、②本人の下書きのうち AI エージェントが書いた版と、いまの下書き・公開版との行の差（サーバーの非 AI の差分。件数と行数に上限）、③AI が作って14日たっても公開していない下書きの数。他人の記事へのレビューの宛先（書いた人）には何も渡さない（C22 条件1の「書いた本人に欄が出ない」を保つ）。差を取るため、エージェントが create_draft／update_draft で書いた本文を、その下書きに紐づけて本人専用で残す（下書きを消すと一緒に消える）。理由：定時実行や claude.ai のコネクタは端末に原本を残せず、別の端末・別のエージェントからも同じ差を読めるようにするため。生の材料はアカウントの外へ動かない（エージェントが読むのは本人が許可した接続の中だけ）。

## 2026-11-22 — アプリ全体の UI を、学生が普段使うメジャーなサービスの型の「キメラ」にする（オーナーの考えを受けた方針）

2. **当てはめの判断は「同じ役目の画面が、学生が毎日使うサービスにあるか」。** あれば置き場所・アイコン・操作の順番をその型に寄せ、部分ごとに別のサービスから借りてよい。2026-11-22 時点の当てはめは ux-rubric の「見比べる型」の表（ヘッダー＝note/Zenn、記事の操作＝note/Zenn/Qiita、通報＝X/YouTube の「…」、エディタ＝Zenn/note、閲覧履歴＝YouTube/Chrome、検索＝YouTube/Zenn、公開停止＝YouTube Studio/note など）。表に無い画面は、作る前に型を探して表に足す。

5. **出し方。** 型の見直しはループの通常の仕事として進める（polish が R0/R1 を直し、R2 や大きい組み替えは `loop:ux` Issue）。既存の Issue と重なるもの（#203 公開停止、#210 画像、#143 内部用語）はそちらに寄せる先を書き足し、新しく立てない。11-24 の宣伝（#217）より前に、学生が使う流れを大きく組み替えることはしない。宣伝直前に形を変えると、検証していない画面で初めての学生を迎えることになるため。
6. 採らない場合の影響：画面ごとに独自の置き場所と説明文が増え、「文字は少なく」を守るために毎回説明を削っては足す後追いになる。逆に型をそのまま写すと、フォロー数や閲覧数のように目的と恒久条件に反するものまで入る（3・4 で止める）。
7. 仮説 H07：同じ役目の画面をメジャーなサービスの型に寄せると、初めての学生が迷う回数（patrol の S2 件数、実利用者の「どこを押せば」の問い合わせ）が減る。未検証。AI の巡回で S2 が減ることは学生にとっての価値の証拠ではなく、確かめるには宣伝後の実利用者の声と、下書きから公開までに離脱した割合を見る。

## 2026-11-22 — #12 の expand：R2 と D1 の両方に書き、読みは R2→D1、key に sha256 を含める

オーナーが R2 を有効化した（#218）。agent が private bucket `kobe-student-hub-media`（APAC、r2.dev 無効・独自ドメインなし）を作り、本番設定に binding `MEDIA_BUCKET` を足した。

1. **expand の間は両方に書く。** `media_assets.payload` は `NOT NULL` と CHECK 付きで、列の条件を変えるには表の作り直し（contract）が要る。いま D1 に書くのをやめると、1つ前の Worker へ rollback した時に R2 にしか無い画像が読めなくなる。R2 に先に書き、失敗したら D1 の行を作らない。D1 が拒んだら object を消し、取り残しは cron（15分ごと）で D1 に行が無く1時間以上たった object を掃除する。
2. **読み出しの認可は D1 だけ。** D1 で所有者・公開状態を確かめた行の id と sha256 から key を作り、R2 の中身を sha256 で照合してから返す。R2 に無い・合わない時は、同じ認可の SQL を payload 付きでもう一度引く（認可を飛ばす経路を作らない）。
3. **key は `media/<id>/<sha256>`。** id は利用者が決めるので、他人が同じ id で上げても別の key になり、既存の画像を上書きできない。
4. 1つ前の Worker が書いた D1 だけの行は、新しい列 `object_stored_at_ms` が NULL のものを cron が R2 へ写す（0031 は列の追加だけ）。R2 の権限が無い deploy 用 token でも R2 binding 付きの deploy は通ることを使い捨て Worker で確かめた（token への権限追加は不要）。
5. 次（contract）：本番でこの版が動き、全行の `object_stored_at_ms` が埋まったら、payload を書かない版と、payload を任意にする表の作り直しを別の列車で出す。#188・#195 の容量上限はその後に R2 の容量で決め直す。プロフィール画像（`profile_avatars`、1枚 64 KiB）は D1 のまま（容量の頭打ちに効かないため）。
6. 採らない場合の影響：R2 だけに書く形にすると rollback で画像が欠け、key に sha256 を入れないと id を使い回した上書きで他人の画像を差し替えられる。

## 2026-11-22 — 続けたくなる体験：積み上がりが見え、届いた手応えがあり、出した瞬間が楽しい（オーナーの考えを受けた方針）

5. 採らなかったもの：全更新の自動マージ。major は API が変わり unit test だけでは足りないことが多く、release の full CI で初めて赤になると列車が止まる。main の全 push に必須 CI を掛ける案も、agent の直接 push を止めるので採らない。
6. 残るすき間：GITHUB_TOKEN のマージは main-health を起こさないので、別々に green だった2本が重なって壊れる場合は release の verify で初めて見つかる。cooldown と週1のまとめ（group）で同時に入る本数が少ないため、今は許容する。

2. 仕組みは新しく作らず、記事のタグで表す。種類のタグ `ごはん`、エリアのタグ `北野川線沿い` をつける（検索の `?tag=` と、関連記事の「同じタグ」がそのまま効く）。店名・場所・評価を DB の列にする（構造化）のは、レビューが積み上がって必要が見えてから。採らない場合の影響：先に列や地図を作ると R2 の migration と外部地図の privacy 設計が要り、レビューが1件もないうちに仕組みだけが増える。
3. エリアの入口（トップや検索からの「北野川線沿いのごはん」）は、公開済みのレビューが3件以上になってから出す。0件の入口は空の約束になるため。
4. レビューの決まり（書き方の案内に入れる）：自分が実際に行った店だけを書く。行った時期を書き、値段・メニューは「その時点」と明記する。店からの無料提供・割引・依頼があれば本文に書く（ステルスマーケティングにしない）。店員や他の客を写真・文章で特定しない。悪い体験は事実として書き、店や人への中傷にしない。
5. agent はレビュー本文・サンプルのレビュー・店の候補一覧をリポジトリや本番に作らない。公開情報から拾った店の候補は「行った店」ではないため（このリポジトリは公開）。レビューの中身は書く本人の経験だけ。
6. 仮説 H02：同じ通り沿いの記事が積み上がると、学生が「次にどこへ行くか」を決める材料として、ばらばらの記事より使われる。未検証。最初の確かめ方は、レビューを読んだ学生が実際にその店へ行ったかを試用（#5）で聞くこと。

## 2026-11-21 — 本番運用と PRD 方針を agent に任せる（オーナー決定）

オーナー（服部）が次を決めた。「AI エージェントが大胆に自律的に進める」方針に合わせるため。

3. PRD 方針は agent が判断して更新してよい。変えた方針はこのファイルに日付と理由つきで記録する。AGENTS.md の恒久条件（本人確認・非公開データ・安全な Markdown など）は PRD 方針ではないので、この権限では緩めない。
4. 人の判断に残すのは、課金・契約、資格情報の発行、実利用者への告知・募集・試用だけ。（資格情報の発行は 2026-11-23 の項で条件つきで agent に移した）

## Architecture

Use TypeScript end to end: React/Vite frontend + Hono Worker + Static Assets + D1. A single Worker origin avoids unnecessary services and cross-origin auth. Tailwind v4 and Base UI follow the PRD. react-markdown/remark-gfm/rehype-highlight avoid custom Markdown parsing, and raw HTML is disabled. No image/iframe renderer in this cycle. Mermaid/YouTube are deferred until their security and privacy conditions are designed.

D1 stores structured public sample content with explicit status. The SQL projection excludes every non-published state and non-sample row, including at final API delivery. No real private fields are added merely to scaffold unused features. Current search loads at most 100 sample entries and filters locally; this is intentionally unsuitable for a production-size catalog. Future indexed search/pagination is a separate task.

No AI inference, embeddings, R2, email or subscriptions are enabled. Related entries use explicit relationships then shared tags; this is not personalized recommendation or popularity ranking. Do not invent likes/counts/history.

Name `kobe-student-hub` is a reversible working name chosen after checking accessible owned repositories. No school logo or official affiliation is claimed. No open-source license for original code has been selected by the owner; public visibility alone is not a license grant. Reference notices are preserved in DESIGN.md.

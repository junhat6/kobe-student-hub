# Local pending review and withdrawal

This prepares a narrow server-only procedure over fictional local data. It is not mounted in `worker/index.ts`, provisions no operator, makes no school-eligibility decision and enables no real signup/login/posting. Use the existing verified pending-registration broker, `SessionStore`, central final SQL guard and account status/epoch/subject-floor triggers; do not introduce a second authentication mechanism or copy an identity from request JSON.

## Explicit review, separate authority

`AdmissionStore.decide()` accepts only a same-origin POST with an existing live session and CSRF proof. An active student account alone is insufficient: an unrevoked, unexpired row in `private_admission_operators` must separately authorize that actor. The operator cannot approve or withdraw its own account. No method or migration grants this role. Actual role provisioning and the initial operator trust chain require a separately reviewed operation; local tests seed fictional roles only.

Approval requires the target to be pending with the exact expected epoch. Withdrawal requires active with that epoch and moves the account to suspended. There is no suspended/deleted reactivation or automatic return to pending. Graduation, correction, reinstatement and recovery remain separate policy decisions. Twelve competing approvals have one winner. A stale/replayed status command cannot repeat its effect or create a second audit.

A successful statement inserts a minimal audit and an SQL trigger applies the target transition atomically. An audit/trigger failure rolls back the transition. Existing status triggers increase the epoch and subject-specific floor: withdrawal rejects existing sessions and older in-flight login/registration for that subject while preserving unrelated students. Approval does not issue a session or create a public profile; the person must make a fresh explicit login.

Both session and operator grant are checked in the final guarded statement after preflight. Time is resampled when final SQL bindings are prepared, as for other repositories; this does not claim a database-commit clock or immunity to arbitrary clock jumps.

The private audit stores internal actor/target IDs, action, expected epoch, an opaque UUID review reference and time/expiry. It stores no school email, Google subject, raw enrollment evidence, free-form reason, token, request, body or secret. An UPDATE trigger prevents rewriting its history; configured expiry maintenance can delete old rows. A reference asserts that an authorized human performed a separate review; it cannot itself establish that the review or eligibility was correct. Audit IDs are not public DTOs.

## Bounded local retention procedure

The server must explicitly supply positive safe durations for `pendingRetentionMs`, `auditRetentionMs` and `maintenanceIntervalMs`; there are no production retention defaults. Tests use fictional timings only. Pending reconfirmation does not refresh creation time or silently extend retention.

`purge()` is privileged server maintenance, not an HTTP route. One atomic batch reserves a persisted interval and deletes at most100 expired never-active pending accounts and100 expired audit entries. Pending deletion requires epoch0, no session row and no operator grant. Active/suspended/deleted/previously transitioned accounts are outside this operation. Account-delete triggers retain the existing revocation floor; old pending proofs cannot recreate an erased request, while a fresh verified registration may create a new pending request. Before deletion, trusted database-schema introspection discovers every current foreign-key reference to accounts; the final DELETE excludes accounts with any such child, including legacy pending rows holding drafts, profiles, reports, likes or publication records. This prevents CASCADE/SET NULL side effects. Schema discovery includes at most100 application tables and100 account references; it excludes only known D1 metadata names and SQLite-reserved internal tables, and otherwise fails closed. Case-insensitive table names, safely quoted identifiers and the actual referenced parent column are respected. The run must be serialized with migrations so new tables cannot appear between discovery and deletion. A storage/trigger failure rolls back the batch.

The run returns counts only; a throttled, malformed-time or failed run returns null. The full deletion/reservation batch rolls back on failure. Discovery is read-only and precedes that batch. A100-row deletion budget does not bound total query work: candidate walks and child lookups can scan accumulated rows, especially with missing child indexes. Review actual-schema query plans, candidate backlog and job duration before production; finite transport-cleanup tests do not establish arbitrary pending-purge capacity. A later deliberate run may drain the next100 after the interval. Backward time cannot advance the job. Audit retention and pending deletion do not promise erasure from provider logs, backups, private evidence, school systems or downstream copies. Actual retention choices, a quiet-period scheduler, backlog monitoring, stop/restore and user explanation remain unconfigured.

Transport capability cleanup is the separate [authentication maintenance procedure](AUTH-MAINTENANCE.md), which reuses existing attempt/floor cleanup and never deletes accounts/audits. Do not combine the two policies merely because both delete rows.

## Issuance workload guards

`BrowserSessionCoordinator` now bounds live anonymous contexts and minute-window commands with conditional SQL insertion. The defaults (10000 live contexts and20 commands per context per minute) are conservative local preparation values, not measured production capacity or enrollment limits. Trusted server options can lower these maxima and cannot exceed them or use malformed/unbounded values. Expiry-window indexes are prepared in migration0014.

Login/registration share one start budget; logout has a separate budget so exhausting start commands does not prevent an urgent logout. Executed commands remain in their window's count, preventing execution from resetting the quota. Concurrent inserts cannot exceed each configured limit, and rejected insertion issues no cookie/command or generation advancement. Fixed context expiry and the normal minute boundary allow recovery.

These controls bound accepted live storage and per-context command bursts; they do not rate-limit new browser contexts by person/IP, stop distributed abuse, bound total incoming request/query cost, or prevent an attacker filling the shared cap. The global capacity limit can deny legitimate sign-ins. Trusted edge-level rate controls, workload measurement and abuse response remain production requirements. Existing opportunistic floor cleanup still runs before issuance and can inspect accumulated records; see maintenance query-plan/finite-backlog evidence and its limits.

## Safe fictional runbook and unresolved choices

1. Use disposable local D1 and the required migrations, including0013 for admission and0014 for transport maintenance/indexes. Keep the production gate false. Do not copy real subjects, emails, secrets or production rows.
2. Seed one fictional active operator account and a separate bounded role row in the fixture. This is test setup, not an initial-operator provisioning tool. Record the missing actual authority decision.
3. Use the existing synthetic signed registration flow to record a pending target. Verify there is no session/profile. A Google-domain match remains distinct from actual current enrollment.
4. After a fictional review, submit its opaque reference and expected epoch through the server-private operation with the operator's real local session/CSRF. Confirm one audit/active transition. Retry the old command and test another actor, stale session, expired/revoked role and self-operation denial.
5. Make a fresh explicit target login; then withdraw using the exact current epoch. Check its session and old in-flight callback are refused and another fictional student remains unaffected. Do not label suspension as account/content deletion.
6. Choose explicit fixture-only retention/interval values. Advance controlled time, call each maintenance operation once, inspect counts/FK/backlog and invoke again only at the chosen interval. Test rollback and concurrent calls. Keep captures private; return counts/generic receipts only.

Before any real operation, decide who may review, the authoritative evidence and year/graduation rules, appeal/correction and recovery, contact/notification, retention and erasure expectations, initial operator authority and least privilege. A narrowly reviewed server procedure may suffice initially; a new operations UI is not mandatory. This implementation does not answer those decisions. Real login additionally needs the actual logging/transport gate and Google/browser tests; real posting needs its product routes and moderation/privacy/operating gates. No remote migration, role assignment, real account, scheduled job or authentication activation is part of this change.

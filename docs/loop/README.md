## 1. なぜ進め方を変えるか

これまでの約2.5週間で、本番には閲覧・学校Google登録・アカウント機能が載りました。一方で次の傾向がありました。

- **証拠の過剰生産**：`docs/` に QA-*.md を含む約120ファイル、PR本文に receipt SHA256 が並ぶ。検証そのものより「検証したことの記録」にコストが流れた。
- **ゲートの直列化**：PRごとに full CI（e2e・auth・editor の4系統）と別contextQAを待つため、小さな改善も数時間単位になる。
- **価値の検証が後回し**：技術的な安全確認は厚い一方、「学生が使って次の行動につながるか」を確かめる仕組みがない。

慎重さが無駄だったわけではありません。認証・個人情報・本番データは今後も慎重に扱います。
変えるのは「**すべての変更に同じ重さの儀式をかける**」ことです。ここからは、取り返しのつかなさに比例して検証の重さを変えます。

## 2. 原則（8つ）

1. **完成の定義を先に置く。** 「何ができたら完成か」を [completion.json](completion.json) に機械可読で置き、ループはその差分を埋め続ける。定義のない「改善」は永遠に終わらない（Anthropic の長時間エージェント研究で、エージェントが途中で「完成」と早合点する失敗への対策がこれでした）。
2. **1周1仕事、状態はファイルとgitに。** 会話の記憶に頼らない。各周回は台帳・Issue・git log から状況を読み直し、1つの仕事を終えてcommitし、次の周回へ渡す（Ralph ループの核）。長い会話を引き延ばすより、短い周回を何度も回すほうが壊れにくい。
3. **作る人と評価する人を分ける。** エージェントは自分の成果を甘く採点する（Anthropic の評価で確認された傾向）。UX巡回と危険度の高い変更の検証は、作ったセッションとは別のcontextで行う。
4. **検証の重さはリスク段階で決める（下表）。** 戻せる変更は速く出して巡回で拾う。戻せない変更だけ厚く守る。
5. **mainは常に動く、リリースは選んで出す。** main へは直接commitしてよい。本番へは「選んだmainのSHA」だけを昇格させ、そこで初めて full CI を必須にする。
6. **詰まったら止まらずに迂回する。** 同じ仕事で3周失敗したら `blocked` にして次へ進み、まとめて人に報告する。人の判断が要るもの（課金・実利用者・資格情報）は待ち行列に積み、ほかの仕事を続ける。それ以外（本番 migration・deploy・PRD方針を含む）は自分で決めて進め、決めた理由を残す。
7. **記録は最小、学びは残す。** 機能ごとのQA文書は作らない。証拠はcommit本文・Issueコメント・CI artifactへ。ただし「次の周回が同じ失敗をしないための学び」は [AGENTS.md](../../AGENTS.md) か該当ループの指示書に1行で足す（compound engineering の考え方）。
8. **条件が実装を止めたら、条件を疑う。** 受け入れ条件は有限の手順で合否が決まる形で書く。同じ item が毎回違う理由で fail し続けたら、実装を足すのをやめ、条件と設計の側を見直す（replan。弱める・消すことも判断し、理由を [DECISIONS.md](../DECISIONS.md) に残す）。境界の設計と条件の書き方は [DESIGN-PRINCIPLES.md](DESIGN-PRINCIPLES.md)。

### リスク段階（検証の重さ）

| 段階 | 例 | main へ入れる前 | 本番へ出す前 |
| --- | --- | --- | --- |
| **R0 戻せる** | 文言、見た目、レイアウト、空状態、文書、テスト追加 | build と関係するテストを自分で実行 | release CI |
| **R1 振る舞い** | 画面の導線、公開APIの読み取り、検索・推薦ロジック | 上記＋自分でブラウザ確認（PC/モバイル） | release CI＋UX巡回1回 |
| **R2 境界** | 認証・権限・所有者チェック、非公開データ、通報・運営、ログ、D1 migration、本番データ操作、PRD方針の変更 | 上記＋**別contextの独立検証**（観点は AGENTS.md の恒久条件）。PRD方針は [DECISIONS.md](../DECISIONS.md) に理由つきで記録 | release CI＋独立検証。migration は expand のみで、適用は release の deploy が Time Travel ブックマークを残してから行う |
| **R3 人の判断** | 課金・契約、資格情報の発行、実利用者への告知・募集 | 実施しない。[人の待ち行列](LOOPS.md#人の待ち行列)に積む | 人が決めた後に R2 として扱う |

## 3. 全体図

```text
                         ┌──────────── 人（レビュー・判断・学生の声） ─────────────┐
                         │  R3の判断 / 完成台帳の修正 / UX採点の較正 / 学生検証     │
                         └───────▲──────────────────────────────┬──────────────────┘
                                 │ 報告（HTML1枚＋結論1〜2行）     │ 決定
 ┌───────────────────────────────┴──────────────────────────────▼──────────────────┐
 │  再計画ループ (replan)  台帳と現実の差分 → Issue待ち行列を作り直す（数時間ごと）    │
 └───────▲──────────────────────────┬──────────────────────────────────────────────┘
         │ 所見                      │ 優先順つきIssue（loop:finish / loop:ux / loop:garden）
 ┌───────┴────────┐        ┌────────▼─────────┐        ┌──────────────────────┐
 │ UX巡回 (patrol) │        │  完成ループ       │        │ 庭仕事 (garden)       │
 │ 別context・読取 │◀──main─│  (finish)         │──main─▶│ 文書の陳腐化・重複・   │
 │ 旅をPC/モバイルで│        │  1周1Issue→commit │        │ 依存更新・死にコード   │
 │ 歩き採点→Issue  │        │  builderレーン×1〜3│        └──────────────────────┘
 └────────────────┘        └────────┬─────────┘
                                    │ 選んだSHA
                           ┌────────▼─────────┐
                           │ リリース列車       │  main → release（full CI必須）
                           │ (release)         │  → tag → 本番deploy → smoke → 失敗なら戻す
                           └──────────────────┘
       内側にはいつも「編集 → 型・テスト → ブラウザ」の速い backpressure ループが回る
       main が赤くなったら、他の全てより先に修理ループ (mend) が直す（アンドン）
```

ループの詳細仕様は [LOOPS.md](LOOPS.md)、誰がどのループを回すかは [SESSIONS.md](SESSIONS.md) にあります。

## 4. 完成とは何か

完成＝[completion.json](completion.json) の全項目が `pass`、かつUX巡回で重大度 S1/S2 の所見が2回連続で0件、かつ本番（release）に載っていること。

これは「開発として完成」の定義です。学生にとって価値があるか（PRDの目的「記事・作品から知識・経験・活動に出会い、次の行動の材料にする」）は、AIの巡回では確かめられません。完成後は、実際の学生に使ってもらう **価値検証ループ** が主役になります（[LOOPS.md](LOOPS.md#6-価値検証ループ-value人が主役)）。

台帳を書き換えてよいのは、人か再計画ループだけです。完成ループのbuilderは `status` と `evidence` だけを更新します（Anthropic の feature_list.json と同じ理由：作業者が完成条件を緩めて「完了」にする抜け道を塞ぐ）。

## 5. リリース方式の思想

**採用：trunk-based（main＝開発トランク）＋ release ブランチへの昇格。** 具体手順と設定は loop-infra セッションが [docs/RELEASE.md](../RELEASE.md) と GitHub ruleset で実装します。

| ブランチ | 役割 | 入れ方 | 必須チェック |
| --- | --- | --- | --- |
| `main`（default） | 開発トランク。常にbuildが通る | 直接push可（短命ブランチ→PRも可）。force push・削除は禁止 | なし（各自の backpressure） |
| `release` | 本番の写し。ここにある＝本番にある | `npm run release` だけで昇格。main の選んだSHAを `rc/<sha7>` へpushし、CIの verify が green なら release へ fast-forward | full CI（verify）必須、bypassなし |

- PRは使わず fast-forward で昇格するので、release 上のSHAは必ず main の履歴に含まれる（「本番にあるのにmainにない修正」が生まれない）。
- 昇格のたびにタグを打ち、GitHub Release を作り、未適用の D1 migration を当ててから本番へdeployし、本番URLへsmokeを当てる。失敗すれば直前の版へ戻す。
- release への直接push・force push は agent hook で拒否する（定義は `.claude/settings.json` と `scripts/loop/`）。本番の運用（deploy・rollback・リモートD1）は hook で止めず、agent が判断する（2026-11-21 オーナー決定）。通常の本番反映は `npm run release` の1本で行い、手順は release skill（`.claude/skills/release/SKILL.md`）にまとめてある。
- 不具合修正も「main で直す → 昇格」が原則。release への直接修正は緊急時だけ。

**この方式を選んだ理由**

- AIの並行セッションは、小さく頻繁にmainへ統合するほど衝突が小さい。長命ブランチ（git-flow の develop/feature）は衝突を後ろへ溜める。git-flow の作者自身が2020年に「継続的デリバリーのWebアプリならもっと単純な方式を」と注記しています。
- それでも本番には「全テストが通ったものだけ」を出したい。そこで Rust（main→beta→stable）や Chromium（main で開発し、選んだ地点を切って出荷）と同じく、**開発の速さと出荷の安全をブランチで分ける**。CIは出荷の関所にだけ置く。
- develop を新設して default を移す方式は採らない。並行セッション全員がいま main を使っており、切り替えのコストと事故の方が大きい。
- release ブランチを1本の「本番の写し」にする（Kubernetes のような版ごとの release-X.Y は作らない）。Webサービスは常に最新1版だけを運用するため、版の並行保守が要らない。

**採らない場合の影響**：全PRでCI必須に戻すと、並行セッションが互いのCI待ちで詰まり、今日の目的（大胆に進める）と衝突します。逆にリリースにもCIを課さないと、e2e でしか見つからない認証・境界の退行が本番に出ます。

## 6. 変えないもの

- AGENTS.md の恒久条件：学校Googleのサーバー側本人確認、所有者チェック、非公開データ（学校メール・認証ID・申告年度・下書き・履歴）、安全なMarkdown、ログに内容・身元・秘密を出さない、秘密をファイルやコマンドに置かない。
- PRD方針は agent が判断して更新してよい（2026-11-21 から）。PRD の原文（オーナーの非公開 Google Doc）は書き換えず、変えた方針は [DECISIONS.md](../DECISIONS.md) に日付と理由つきで記録し、そちらを優先する。
- 「AIの動作確認は学生の価値検証ではない」「PC/モバイルviewportの確認は実機確認ではない」という区別。報告でも混ぜない。

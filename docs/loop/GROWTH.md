# 集客・運用フェーズのループ設計

2026-11-28 策定（オーナー決定：完成度を高めるフェーズを終え、集客・運用へ移る。[DECISIONS](../DECISIONS.md) 2026-11-28）。
完成フェーズの思想（[README](README.md)）のうち「1周1仕事」「状態はファイルと Issue に」「作る人と評価する人を分ける」「リスク段階」「恒久条件」はそのまま使う。
変えるのは**北極星**と**ループの組み合わせ**と**オーナーへの報告の形**です。

## 1. 何が変わるか

| | 完成フェーズ（〜2026-11-27） | 集客・運用フェーズ（2026-11-28〜） |
| --- | --- | --- |
| 北極星 | [completion.json](completion.json)（27 item が pass） | [growth.json](growth.json)（仕組み・健全性・観測の3層） |
| 仕事の出どころ | 台帳の未達・UX 巡回の所見 | 計測の数字・本番の監視・公開された記事・台帳の未達 |

completion.json は凍結する（27/27 pass の記録として残し、書き換えない）。新しい機能の完成条件は growth.json の `items` に書く。

## 2. 目的と、ループが約束すること・しないこと

| # | 目的 | ループが約束する（合否を付ける） | 約束しない（観測して報告する） |
| --- | --- | --- | --- |
| O1 | 使われ方が見える | 流入元・記事の読まれ方が毎日 Analytics Engine に記録され、継続（書き手の再訪と読者の直接来訪）と合わせて週1回の表になる | 数字の良し悪しの判断 |
| O2 | 検索・SNS から人が来る | 公開記事が検索に載る形で配信される（index・メタ情報・sitemap）、X のカードが出る、新しい記事ごとに投稿案が 24 時間以内にできる | 検索順位・流入数・投稿の反応 |
| O3 | 記事が増え、読まれる | 届いた材料が下書きになる、読まれ方の数字が執筆の材料に入る | 学生が書くかどうか、読んで行動したか |
| O4 | 本番が安定して回る | 障害・コスト・不正利用を毎日点検し、閾値を超えたら一次対応して Issue に残す | 外部要因の停止がゼロであること |
| O5 | 書き手が増える（2026-11-28〜12-12 の一番。§10） | 招待リンクから登録・プロフィール・最初の下書きまで迷わず進める導線があり、その所要時間を本番で測ってある。入口→登録→下書き→公開の数が週次の表に集計で載る | 何人が書くか・公開するか |

**流入数・読了率などの成果を合否にしない理由**（[DESIGN-PRINCIPLES](DESIGN-PRINCIPLES.md) 原則3・4）：成果はループが有限の手順で達成できるものではなく、合否にすると「数字を動かす」こと自体が目的化する（グッドハートの法則。計測の分野で枯れた結論、原則6）。ループが責任を持つのは「仕組みがあり、動き、数字が届く」ところまで。数字を見て方向を決めるのはオーナーで、その判断が楽になる形で届けるのがループの仕事（原則4：責任の所在を設計する）。
**採らない場合の影響**：成果目標を合否にすると、replan が満たせない item を延々と Issue にし、builder がクリックを稼ぐ小手先の変更（煽る見出し、通知の乱発）に寄る。

| `ksh ops` | 新規 | **作る** | 毎時 precheck で本番の smoke、落ちたら一次対応。動いていれば 1 日 1 回、障害・コスト・不正利用を点検して ops-log へ |
| `ksh outreach` | 新規 | **作る** | 毎日 18:30。新しく公開された記事ごとに X の投稿案（完成文）を作り、週1回 SEO の配信状態を点検する |

**ループを増やす理由**（[SESSIONS](SESSIONS.md) の「分ける理由は3つだけ」）：measure・ops・outreach は書き込み先（growth-log・ops-log・outreach-log の Issue）と読むもの（計測・本番の監視・公開記事）がそれぞれ違い、1つの係に詰めると context を食い合う。どれも precheck で「やることが無ければ起こさない」ので、増えるのは起動の判定だけ。

### オーナーの手間を判断だけにする

- オーナーが見るのは **growth-log の週次コメント1つ**（月曜）。中身は「先週の数字（表3つ）」「ループがしたこと」「判断してほしいこと 0〜3件（選択肢と推奨つき）」だけ。判断が要らない週は「判断なし」と書く。
- X の投稿は**オーナーの手で行う**（投稿の権限を agent に渡さない：アカウントの声と責任はオーナーにある。原則4）。outreach は「そのまま貼れる完成文」と「付けるリンク（utm つき）」まで作り、outreach-log に置く。使うかどうか・いつ出すかはオーナーが決める。
- `needs-human` は課金・契約と、オーナーのアカウントでしか開けない場所（Search Console の所有権確認など）だけ。

## 5. 計測（O1）

**採用：自前の受け口（`POST /api/usage`）→ Workers Analytics Engine（dataset `ksh_usage`）。**

| 選択肢 | 採らなかった理由 |
| --- | --- |
| PostHog（オーナーの候補） | 無料プランは1組織1プロジェクトで、既に Idea Boost が使っている。別組織を作れば無料で使えるが、閲覧の記録を新しい第三者（米国）に渡すことになり、情報の扱いの変更が大きくなる。PostHog の画面（ダッシュボード）は、オーナーが週次の表だけを見る運用では使わない |
| Cloudflare Web Analytics | cookie なしで手軽だが、記事ごとの読まれ方（どこまで読んだか）と再訪が取れない。外部スクリプトのため CSP の `script-src 'self'` を緩める必要がある |
| D1 に書く | 閲覧のたびに本番 DB に書くと、書き込みの上限と費用が閲覧数に比例して増える。計測の行が利用者のデータと同じ場所に混ざる |

Analytics Engine を選んだ理由：既に契約している Workers Paid の中で使え（原則5：持っている資源に乗る）、配信を任せている Cloudflare から外にデータが出ない（原則2：データを動かさない）。CSP も変えずに済む。読むのは agent が Cloudflare MCP の SQL API（`POST /accounts/{id}/analytics_engine/sql`）で行う。

**送るもの（ホワイトリスト。`src/shared/usage-event.ts` の `usageRow` が列挙以外を丸ごと捨てる）**

| 列 | 中身 |
| --- | --- |
| index1 | 匿名の識別子（ページを開くたびにブラウザがランダムに作り、メモリの中だけに持つ。保存しない・アカウントと結ばない） |
| blob1 | `view`（画面を開いた）／`read`（記事・作品を離れた） |
| blob2 | 画面の種類（`home` `search` `works` `article` `project` `student` `about` `guide` `agents` `write` `account` `other`） |
| blob3 | 記事・作品の公開 ID（それ以外の画面は空。学生のハンドル・下書きの ID は残さない） |
| blob4 | 来たサイトのホスト名だけ（セッションの最初の view。パス・検索語は残さない） |
| blob5〜7 | `utm_source` `utm_medium` `utm_campaign`（英小文字・数字・`-_.` の 40 文字まで） |
| blob8 | 匿名の識別子（index1 と同じ。SQL で数えやすくするため） |
| blob9 | セッションの識別子（30 分無操作で変わる） |
| blob10 | `m`（幅 768 未満）／`d` |
| blob11 | ページを開いて最初の view なら `1`（着地ページを数えるため） |
| double1 | read：どこまで読んだか（0〜100%） |
| double2 | read：画面が見えていた秒数（0〜3600） |

送らないもの・残さないもの：ブラウザの保存領域（localStorage・sessionStorage・cookie に何も書かない。このサイトの既存の決まりで、ブラウザ検査が全画面で確かめている）、cookie（`credentials: 'omit'`、cookie つきの要求は 400）、IP（Worker が書かない）、アカウント、学校メール、URL のクエリ（utm 以外）、本文、クリック、画面の録画。Do Not Track・Global Privacy Control が有効なら何も保存せず送らない。明らかな bot の UA は数えない。Analytics Engine の保存は 3 か月で、それより古い行は Cloudflare が消す。情報の扱い（`/guide#privacy`）に同じことを書いた（2026-11-28 改定）。

**週次の表（measure が SQL で作る）**：

1. 流入元：セッション数を `blob4`（ホスト名を「検索」「X」「その他SNS」「直接」に寄せる）と `blob5` で
2. 記事の読まれ方：記事ごとの view 数・read の中央値（深さ・秒）・75% 以上読んだ割合
3. 継続：読者は識別子を保存しないので再訪を個人単位では数えない。代わりに (a) 直接来訪（参照元も utm も無いセッション）の割合と数の推移を読者の再訪の目安にし、(b) 書き手（ログインするアカウント）は本番 D1 の活動時刻から週の活動アカウント数と前週からの継続数を集計する（集計だけ。5 件未満は「5 未満」）

**再訪を識別子で数えない理由**：数えるには識別子をブラウザに保存する必要があるが、このサイトは「ブラウザに何も残さない」ことを下書きの保護として全画面で守っている（ブラウザ検査が localStorage・sessionStorage が空であることを確かめる）。計測のためにこの決まりを崩すと、下書きの保護の検査が「計測の分だけ例外」になり、決まりが弱くなる（原則1：例外を足すより、渡すものを決める）。読者の再訪は推定で足り、継続が大事なのは書き手で、書き手の活動は既にサーバーにある（原則2）。

## 6. 検索と SNS（O2）

- **検索エンジンへの掲載を始める**（noindex 方針の変更。[DECISIONS](../DECISIONS.md) 2026-11-28）。index してよいページを列挙する：`/`、`/works`、公開記事 `/articles/:id`、公開作品 `/projects/:id`。学生のページ・検索結果・アカウント・下書き・API は noindex のまま（原則1）。実装は finish が growth.json の G03〜G05 として行う（R2：公開範囲の方針と情報の扱いの変更）。
- **ページごとのメタ情報**：記事・作品のページは Worker が HTML の head に題・概要・カード画像・canonical を入れて返す（X のカードと検索結果の見え方。今は全ページ同じ1種類）。
- **X の投稿案**：outreach が新しく公開された記事ごとに作る。リンクは `?utm_source=x&utm_medium=social&utm_campaign=owner` を付ける（オーナーの告知と、記事ページの共有ボタンからの自然な共有を分けて数えるため。共有ボタンの URL には付けない）。
- **Search Console**：所有権の確認はオーナーの Google アカウントでしかできないので `needs-human`。登録されたら sitemap を送る。

## 7. 運用（O4）

ops が毎日見る閾値（growth.json の `health`）。超えたら一次対応して Issue に残す。

| 観点 | 見るもの（Cloudflare MCP） | 閾値 → 対応 |
| --- | --- | --- |
| 障害 | 本番の smoke（precheck が毎時）、Worker の 5xx の割合（24 時間） | smoke 失敗 → 直前の版へ戻すか hotfix（release skill）。5xx 1% 超 → P0 |
| 費用 | Workers の要求数・D1 の読み取り行・R2 の容量（月の見込み） | 契約の含み分の 50% 超 → P1 Issue（原因と対策）。プランの変更が要るなら needs-human（R3） |
| 不正利用 | 未対応の通報、1日の新規登録・MCP 接続の急増、計測の1識別子からの大量送信 | 通報は[実利用者に関わる運営](LOOPS.md#実利用者に関わる運営)の決まりで対応。急増は原因を確かめて P1 |
| 計測が生きているか | Analytics Engine の直近 24 時間の view 行 | 0 行（release 後）→ P1 |

公開 Issue に書くのは件数と記録番号だけ（[実利用者のデータ](LOOPS.md#実利用者のデータ)）。

## 8. 受け入れ条件の置き方（growth.json）

3層に分ける。

| 層 | 何か | 合否 | 誰が |
| --- | --- | --- | --- |
| `items` | 一度作れば済む仕組み（受け口・sitemap・メタ情報・報告の形） | pass / unverified / fail。completion.json と同じ決まり（builder は status/evidence/production だけ、条件の書き換えは replan） | finish が作り、replan が台帳を持つ |
| `health` | 毎日満たし続ける条件（本番が応答する・計測が届く・費用が閾値内） | 点検のたびに ok / ng。ng は Issue になる | ops・measure |
| `observe` | 成果の数字（流入・読了・継続・記事数） | 合否なし。週次で表にして報告する | measure が出し、オーナーが判断する |

item を足すときは [DESIGN-PRINCIPLES](DESIGN-PRINCIPLES.md) の「条件を書く・見直すときの確かめ」6問に当てる。成果の数字を item の acceptance に入れない（§2）。

## 9. 変えないもの

AGENTS.md の恒久条件、リスク段階と R2 の独立検証、記事の初めての公開は人だけ、main → release の昇格方式、実利用者のデータの置き場所。

## 10. 書き手の導線（O5。2026-11-28〜12-12 の一番）

オーナー決定（[DECISIONS](../DECISIONS.md) 2026-11-28）：次の 2 週間は書き手を増やすことを集客の一番に置き、最初は Web 系サークル 1 つに声をかける。オーナーが声をかけ、学生が書く。ループが持つのは「迷わず 1 本目の下書きまで行ける」と「どこまで進んだかが見える」まで。

**入口（G10）**：招待リンクは登録画面に utm を付けたもの。

```text
https://hub.junhat6.com/signup?utm_source=circle&utm_medium=invite&utm_campaign=<記号>
```

- `<記号>` は `c1` `c2` のような意味を持たない記号。どの集まりかの対応表は `~/ksh-private/` にだけ置く（集まりの名前を公開物に書かない）。
- 専用のページは作らない。何を書けばよいかと 2 つの道（画面・自分の AI）は、オーナーが送る 1 枚の案内で伝え、サイトの側は登録画面から始める（画面を増やすより、既にある登録→プロフィール→下書きの道の詰まりを取る。AGENTS.md の UI の決まり）。
- 道は 2 つ：**画面**（登録 → 学校 Google → プロフィール → 「最初の記事を書く」→ 新しい下書き）と、**自分の AI**（同じく登録・プロフィールの後、[/agents](https://hub.junhat6.com/agents) の MCP の URL を自分の AI に登録し、AI が下書きを作る。公開は本人が画面で）。

**手順の計測（G11）**：初めての人の道を本番で通し、ステップ・操作数・時間・詰まりを表にして Issue に残す。目標は合計 10 分以内。超えた所・詰まった所は `loop:growth` の Issue にする。導線の画面を変えた release の後に測り直す。既存のアカウントでは通れない段（学校 Google の初回の同意、プロフィールを初めてつくる）は、ローカルの e2e（`tests/ordinary-profile-self-entry-browser.spec.ts`）の操作数で補い、そう書く。

**週次の表（G12・M7）**：measure が月曜の週次に 4 段を載せる。

| 段 | 数え方 | 置き場所 |
| --- | --- | --- |
| 入口 | `utm_medium = 'invite'` で始まったセッション数（`utm_campaign` 別） | Analytics Engine `ksh_usage`（blob6・blob7） |
| 登録 | その週に新しくできたアカウント数（`private_accounts.created_at_ms`） | 本番 D1（読み取りだけ） |

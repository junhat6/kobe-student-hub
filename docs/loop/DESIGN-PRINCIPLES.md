# 境界と条件の設計原則

2026-11-22 記録。C21（自分の AI エージェントとの接続）で、執筆キットの伏せ字（#214）が独立検証3回不合格で止まり、MCP＋学校Googleでの接続許可に作り直した件から、オーナー（服部）とヨッチが抽象化した学び。
個別の経緯は [DECISIONS.md](../DECISIONS.md) の 2026-11-22 の2件にある。ここには、次の機能・次の受け入れ条件にも効く形だけを置く。

**誰が使うか**：replan が completion.json の item を足す・分ける・`blocked` を読み解くとき、人が acceptance を書くとき、builder が「同じ所で何度も落ちる」と気づいたとき。

## 6つの原則

| # | 原則 | ひとことで |
| --- | --- | --- |
| 1 | 伏せるより、渡すものを決める | ブラックリストでなくホワイトリスト・構造化 |
| 2 | データを動かすな、境界を動かせ | 生データは所有者の側、成果物だけが認証付きで越える |
| 3 | 受け入れ条件は検証できる形で書く | 同じ項目の fail が続いたら条件・設計を疑う |
| 4 | 保証の代わりに責任の所在を設計する | 正当なアクセス権を持つ相手には、リスク明示＋同意＋免責 |
| 5 | 利用者が既に持っている資源の上に乗る | 運営が全部抱えるとコストも責任も増える |
| 6 | 新しく見える問題も、枯れた分野で結論が出ている | 作り込む前に隣の分野の定説を引く |

### 1. 伏せる（ブラックリスト）より、渡すものを決める（ホワイトリスト・構造化）

- **なぜ**：範囲が無限の入力（任意の履歴・自由文・任意のファイル）に対して「危ないものは全部伏せた」という全称の保証は作れない。検査を強めるほど、検証役は次の新しい形を見つける。#214 は秘密の形を正規表現で後追いし、3回とも別の形で不合格になった。
- **どう使う**：境界を越えるものは「決めた項目だけ・決めた型だけ」にする。公開 API が明示的な公開 DTO だけを返すのと同じ考え方（[AGENTS.md](../../AGENTS.md) の恒久条件）。MCP の書き込みも「タイトル・本文・タグの下書き」という型に絞る。
- **採らない場合**：検査対象を増やす作業が収束せず、取りこぼし1件が「約束違反」になる。

### 2. データを動かすな、境界を動かせ

- **なぜ**：生データ（ローカルの履歴）をサイト側へ運んでから守ろうとすると、運んだ瞬間に保証問題が生まれる。生データを所有者の側に残し、所有者が作った成果物（下書き）だけが認証付きで境界を越える形にすれば、「生データを守れるか」という問いそのものが無くなる。
- **どう使う**：設計の初めに「生データはどこにあり、誰がもう読めるか」「境界（端末の外・サイトの中・公開）はどこか」を書き出し、境界の検査をサーバーと本人が押さえられる地点（受け口・公開操作）に置く。
- **採らない場合**：サイトが配った道具が利用者の端末内で何をしたかに責任を負うことになり、検証も保証もできない範囲を抱える。

### 3. 受け入れ条件は「検証できる形」で書く

- **なぜ**：「秘密を全部伏せる」のように全称で閉じない条件は、verifier が反例を1つ出すたびに fail になり、ループを無限に止める。builder は実装を直し続け、条件は誰も疑わない。
- **どう使う**：acceptance は、有限の手順で合否が決まる形にする（「この型以外は受け付けない」「本人以外の下書きは 404」「公開の手前で免責4点を表示する」）。ベストエフォートの部分は「合否に含めない」と明記する。
- **fail が繰り返されたときの反応**：同じ item・同じ Issue で fail が2回続き、毎回**違う理由**で落ちているなら、実装ではなく条件か設計の側を疑う。builder はそれ以上実装を足さず、方針変更の提案を Issue に書いて `blocked` にする。replan は原則1〜5で条件を見直し、書き直しで足りなければ acceptance を弱める・消すことも判断する（2026-11-23 オーナー決定。理由と変更前後の文を DECISIONS に残し、恒久条件の手前までしか下げない）。毎回**同じ理由**で落ちるなら、まだ実装の問題。
- **採らない場合**：#214 のように、収束しない後追いに周回を使い続け、その item に依存する機能（C21 と過去セッションからの執筆）が止まる。

### 4. 保証の代わりに、責任の所在を設計する

- **なぜ**：既に正当なアクセス権を持つ相手（本人のマシンで本人の権限で動く本人のエージェント）に対して、サイトが「安全を確約する」のは比例しない。相手は配布物が無くても同じデータを読める。確約は安全を足さず、守れない約束だけを足す。
- **どう使う**：相手が誰で、既に何にアクセスできるかを先に確かめる。正当な権限を持つ相手なら、リスクを明示し、同意を取り、免責を示す（C21 では過去セッションを材料にする手前の免責4点）。補助はベストエフォートとして配ってよいが、確約の言葉で書かない。権限を持たない相手（他の利用者・公開閲覧者）に対しては、従来どおり境界で守る。
- **採らない場合**：確約を求め続けると機能全体が止まる。逆に免責を示さないままベストエフォートにすると、利用者が「サイトが伏せてくれる」と思い込んで確かめずに渡す。

### 5. 利用者が既に持っている資源の上に乗る

- **なぜ**：利用者は AI サブスクリプション・自分のエージェント・自分の端末と履歴を既に持っている。運営側で推論を動かすと、費用（R3 の課金）と、生データを預かる責任が両方運営に移る。
- **どう使う**：運営が持つのは「認証」と「データの受け渡し・保存」、そして境界での規則検査まで。推論・執筆・定時実行は利用者側の能力を使う（[DECISIONS.md](../DECISIONS.md) の C21 の設計の制約）。新しい機能を考えるとき「これは利用者の手元に既にあるか」を先に問う。
- **採らない場合**：運営のコストと責任が利用者数に比例して増え、利用者の履歴を運営が持つことになる。

### 6. 新しい問題に見えても、枯れた分野で結論が出ていることが多い

- **なぜ**：C21 の詰まりは、2つの既存分野の定説で解けた。MCP のスコープ設計（認証・ツールの絞り込み・返却データの最小化）と、秘密スキャン分野の「検出はベストエフォートで多層防御の一部であり、保証ではない」という明文化された立場。
- **どう使う**：受け入れ条件や境界を新しく作る前、また原則3の「繰り返し fail」に当たったとき、隣の分野（認証・認可、秘密スキャン、DLP、サンドボックス、API 設計、プライバシー法制など）が何を約束し、何を約束していないかを調べる。調べた出典は DECISIONS.md の該当エントリに残す。
- **採らない場合**：既に誰かが「保証できない」と結論した問題に、自前の保証を作ろうとして周回を使う。

## 条件を書く・見直すときの確かめ（replan と人が使う）

1. この条件は、有限の手順で合否が決まるか。全称（「全部」「必ず漏れない」）で書いていないか。（原則3）
2. 境界を越えるものを「列挙して許す」形になっているか。「列挙して拒む」形になっていないか。（原則1）
3. 生データを運ばずに済む設計を検討したか。境界の検査はサーバーか本人が押さえる地点にあるか。（原則2）
4. 守る相手は誰か。正当なアクセス権を既に持つ相手に、確約を課していないか。（原則4）
5. 運営側で新しく抱えるもの（推論・保管・定時実行）は、利用者側に既にないか。（原則5）
6. 同じ問題を扱う既存分野の定説を1つ以上引いたか。（原則6）

# 制作ノートを、技術選定の条件と根拠へつなげる

## 仮説と範囲

AIと制作したときも、データ・使い方・性能条件から選んだ方法と確かめた範囲を短く残せれば、次の技術選定や作品説明へ再利用できるのではないか。学生価値の成功は未確認であり、実装QAや運営の参考実験とは分ける。PRD原文と私的な回答は公開文書へ転載しない。

対象は既存の架空sample `learning-notes`一件。題名・投稿者・関連先と既存画面を維持し、本文・概要・想定読者・前提知識・読後説明を更新する。新しい試用機能や記事、実ユーザーの投稿は追加しない。

## 受入条件

- 冒頭で結論を示す。AIにコードを任せた制作から、条件・候補・採用理由・確認の範囲を説明する具体例へつなげる。
- 生成CSVの集計を例に、行数だけでなく容量・問い合わせ方・一人での利用・性能条件を示す。起動/import後のCSV処理10秒以内という目標は測定前に固定し、結果に合わせて変更しない。
- DuckDB／SQLiteを同じデータ・同じSQL・生成時の期待値で確認する。CSVから結果までと取込済みtable queryを分け、測定環境・範囲・限界を残す。速度の一般順位や架空の性能値を作らない。
- 架空の制作／説明、運営の参考実測、公式仕様を区別する。実学生の経験や就職成果として語らない。
- 書き出しの枠は「条件・判断・確認」の3項目。各一文で始められ、別名で多数の必須項目を詰め直さない。
- 条件が変わった次の制作で選び直す場面と、作品説明で自分の判断・AIの担当・未確認を説明する場面を具体化する。

## 保存と公開反映

適用済みmigrationとeditorial0002は変更しない。0003と逆操作を追加し、対象の全15列が直前の値と一致するときだけ変更する。再実行は0件、他編集・private・non-sampleを保護する。local初期化とWorker fixtureも0003まで揃える。

実D1の一件更新・全列の変更保護・逆操作・他row保持、PC/mobileの本文・table・SQL／3行枠のコピー・投稿者／関連導線を実装者と別コンテキストでQAする。参考実験も元resultsを保持した独立再計測でfixture／結果／計測範囲を確認する。タイミングの厳密一致を合格条件にはしない。

必要なlocal check・通常CIとmain統合後、既存の本番対象を私的に照合し、公開済みsampleの旧値を確認したうえで0003だけを適用する。schema/auth/grant/Worker設定の変更や再配備は含まない。実適用後は別担当のGET-only確認を行い、正確な結果を[EVIDENCE](EVIDENCE.md)とPRへ残す。学生の実践・理解は、その後の本人の回答で別に判断する。

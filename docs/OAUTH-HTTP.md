# OAuth HTTP adapter and closed release gate

This is local integration preparation, not a live login/signup release. The production entry keeps an explicit source-controlled release gate disabled. Runtime configuration alone cannot open ordinary login/signup, even if every credential is valid. The existing anonymous sample catalog and `writesEnabled:false` remain unchanged. Real callback protection must pass [LOGGING-GATE.md](LOGGING-GATE.md); configuration and local tests cannot attest platform secrecy or student eligibility.

## Current ordinary registration and sessions

The Cycle49 server-generation protocol remains behind the unchanged disabled production source gate. See [context generation, subject-scoped revocation and session acceptance](SESSION-GENERATION-IMPLEMENTATION.md). Bootstrap and a one-use context/generation-bound command are required before OAuth start. Every final private SQL checks current session authority. Late old cookies are rejected as signed-out and may require fresh login. Historical Cycle45/46 sections below do not describe the current session acceptance rule.

Ordinary self-registration now combines server-verified school Google identity with two required, private self-declared academic years. It does not require manual enrollment approval or document submission, and it does not claim school-certified enrollment. The accepted [participation policy](adr/0001-self-declared-enrollment.md) and [glossary](../CONTEXT.md) distinguish an active account from current student participation. The canonical year/window contract is [src/shared/enrollment.ts](../src/shared/enrollment.ts); the new tables are prepared by migrations [0016](../migrations/0016_self_declared_enrollment.sql) and [0017](../migrations/0017_self_registration.sql). Neither migration has been applied remotely by this implementation. Production signup remains closed.

## Current proof transport

Browser command and CSRF proofs now use the shared purpose-bound Authorization format; old custom proof fields are rejected without fallback. [Transport grammar, logout dispatch and privacy limits](AUTH-PROOF-TRANSPORT.md). The source release gate remains false.

## Configuration contract

The adapter accepts optional request-scoped bindings rather than reading process environment or keeping mutable configuration globally. No actual origin, provider project/client, user contact, key or secret is committed. The deployment configuration and generated Env still describe the existing sample bindings. Optional authentication input types describe validation, not installed secrets or a new secret store.

| Input | Intended future placement | Validation / scope |
| --- | --- | --- |
| `AUTH_ORIGIN` | Non-secret server configuration | Exact canonical HTTPS origin, without path/query/fragment/userinfo |
| `GOOGLE_CLIENT_ID` | Non-secret server configuration | Dedicated Web client audience, bounded provider format |
| `GOOGLE_CLIENT_SECRET` | Worker secret binding | Bounded printable secret; never client assets or public vars |
| `OAUTH_COOKIE_KEY` | Worker secret binding | Canonical base64url encoding of exactly 32 bytes |

Cloudflare [secret bindings](https://developers.cloudflare.com/workers/configuration/secrets/) expose encrypted text through the Worker environment; ordinary vars are not encrypted. Choosing a specific Worker, access scope, safe custody and the mechanism for generating/inserting real credentials requires a separate concrete operation. This change creates none. No required-secret declarations are added to the sample config: absent authentication inputs must keep the existing sample deployable. Later dedicated deployment configuration must declare and generate matching types for its actual bindings.

## Deliberate limits

With an explicitly enabled local adapter and fully valid fictional configuration, the transport contract is:

| Endpoint | Behavior |
| --- | --- |
| `POST /api/auth/bootstrap` | Anonymous one-time context only; no account/session/attempt |
| `POST /api/auth/command?action=<intent>` | Ordinary intents are `login` and `self-registration`; issues a one-use context/generation-bound start command, with no actor or session recovery |
| `POST /api/auth/start` | Same-origin command with `Authorization: Bearer command.<proof>` starts the existing login purpose; no payload-derived authority |
| `POST /api/auth/register` | Same-origin command with `Authorization: Bearer command.<proof>` and exact two-field JSON, such as `{"admissionYear":2026,"graduationYear":2028}`, starts ordinary self-registration; no client identity, owner, status or eligibility flag is accepted |
| `GET /api/auth/callback` | Tries the login claim, then only an unmatched claim may try the distinct sealed self-registration purpose; consumed failures never restart exchange. Every handled ordinary outcome redirects to the same fixed clean root. Callbacks never write the attempt cookie; its original expiry applies. Successful ordinary login or self-registration appends a session cookie |
| `GET /api/private/session` | Reuses existing private handler: CSRF only on authenticated inspection; missing/invalid and unavailable remain distinct |
| `POST /api/private/logout-command` | One-use context/action/generation command, usable with an obsolete session Cookie; no actor/session authority |
| `POST /api/private/logout` | Confirms context generation invalidation with current-session CSRF or a one-use context logout command; no Cookie deletion |

Registration requires `application/json` and two integer academic years in the canonical 1900–2199 range, with graduation year at least admission year. The parser bounds input to 128 bytes and 128 chunks, including empty chunks, and enforces a five-second deadline through EOF. Cancellation is not awaited. Malformed, oversized, stalled or length-mismatched bodies return generic failure without a cookie, command execution or attempt creation. Validated years are stored with the exact executed command/attempt. The underlying database action/intent remains `login`; a distinct encrypted-cookie audience ending `|self-registration` and immutable attempt metadata distinguish ordinary registration before claim. The years never enter Google's authorization URL.

After actual Google verification, one D1 transaction resolves the stable Google subject, creates a new account or activates an existing pending account, stores an initial declaration, issues its session and completes the attempt. The transaction records and checks its exact pending-to-active epoch/fence transition; failure rolls back all partial registration changes. An existing active account without a declaration can explicitly supply one. Existing declarations are retained on later registration callbacks; corrections use the separate private version-checked enrollment form. Suspended/deleted accounts are refused, stored contact is not overwritten, and another subject's matching email never links accounts. Ordinary login still creates no account.

Matched transport responses use private/no-store, Cookie variance, no-referrer, nosniff and noindex. Invalid configuration returns a generic unavailable response before database or provider work; an unexpected origin is refused. With the source gate false and no valid explicit legacy pilot policy, production preserves the previous API fallback rather than exposing a configuration probe. A malformed callback never reflects its query, and the redirect has no caller-selected return URL.

The fixed clean landing page has no authentication-result UI; its redirect alone is not a registration receipt or proof of success. The adapter does not mount the editor, enrollment form, profile, draft, publication, moderation or other account-management routes. Identity sessions and private ownership remain separate from student participation: current student contribution statements additionally check the saved declaration and freshly sampled server time. An ended or missing period does not itself suspend the account or prevent base-session inspection/logout, own-data reading/cleanup or year correction. The [participation policy](adr/0001-self-declared-enrollment.md) defines the app's JST academic-year interval; it does not infer the school's actual calendar or course length. Recovery, retention and operational release conditions remain separate.

Local signed provider responses and D1 data are fictional. Test-only signing, identity injection, fault hooks and private JSON harnesses must never be imported by production. Raw request code/state, provider payloads, identities and session internals must not be logged or reflected in a public response. Outbound authorization deliberately includes the protocol state/nonce/PKCE values; server code exchange deliberately sends the code/verifier/client secret to Google's fixed token endpoint. That protocol exchange is distinct from disclosure in the clean landing page or JSON.

Actual Google browser redirects, SameSite/cross-site behavior, platform/CDN/browser logging, physical devices and student-value validation remain unverified by local HTTP tests. A successful current-session read discloses only CSRF to its same-origin holder; it is not a public identity API. Logout revokes the current session with existing CSRF and final-write checks; it does not revoke every session or undo completed writes. The existing session lifetime still applies to a previously issued session replaced by a later browser login.

Before any real release: verify the exact origin/callback, provider/public information and credential custody, dedicated deployment/database targets and migration ledger; handle required remote changes as distinct verified operations under [DEPLOYMENT.md](DEPLOYMENT.md); finish actual log/transport and operating release gates; then review the source gate and browser lifecycle under real configuration. Adopting the declaration policy or passing fictional tests does not complete those gates. No environment flag is a substitute for those steps.


## Historical request-time attempt-cookie ownership (Cycle45; superseded by Cycle46)

A later start replaces the single browser attempt cookie. A stale callback carrying that newer cookie has no authority to clear it: only a non-null broker result, after a matching one-time claim, supplies attempt removal. Malformed/missing/mismatched callbacks, replay losers and unconfirmed claim failures retain the same clean303/private headers without any Set-Cookie. Matched denial, verification/exchange failure and successful completion still remove the claimed attempt; only active login adds a session. Existing session cookies are not removed by callback failure.

The fixture regression applies every response's Set-Cookie to a shared jar before the next request. It reproduces A-start/B-start/stale-A-with-B-cookie and verifies B can complete after the stale response, along with matched failures, cross-purpose registration/login, replay, concurrent callbacks and DB/cookie refusals. These are local signed fictional provider/Worker/D1 tests, not a browser SameSite or real Google test. See [independent QA](QA-OAUTH-COOKIE-OWNERSHIP.md).

This is request-time ownership, not an atomic browser compare-and-delete. If A already matched and claimed with cookie A, then B starts before A's delayed clearing response arrives, the shared cookie name can still be affected by response order; that separate race is not solved here. [RFC6265 storage and concurrent-response semantics](https://httpwg.org/specs/rfc6265.html#storage-model) describe replacement by cookie identity rather than by its previous value. A null result after an ambiguous DB failure does not prove whether a claim committed. Do not reset consumed markers or automatically replay an exchange; the attempt may require a fresh start or expire. No new cookie format, schema, provider configuration, operational key or production gate change is made.

## Historical Cycle46 investigation — ordering finding superseded by Cycle49

This section records the Cycle46 investigation and proposed next steps. Its attempt-cookie rule remains current; its session-ordering blocker and proposed coordination work predate the gated Cycle49 implementation linked above.

Callbacks now never set or delete `__Host-kobe-oauth`, including matched denial, provider/verification failure, registration and successful login. Only start writes that cookie. This also prevents an already-claimed A response from deleting B after B starts; matching the request cookie cannot authorize a later browser compare-and-delete. Lower-level `clearCookie` return fields remain for API compatibility but the HTTP adapter ignores them. No attempt schema or format changes.

The encrypted cookie can remain for the rest of its original maximum600-second browser lifetime after consumption, instead of being removed early. It contains state, browser binding and PKCE verifier plus JWT context/time claims, without code, provider tokens, client secret or session token. AES-GCM encryption and host-only Secure/HttpOnly/SameSite=Lax attributes remain; callbacks neither refresh the cookie nor its JWT expiry. Atomic DB consumption still rejects replay, and JWT/DB expiry refuses an unconsumed old attempt even if a client ignores browser expiry. Retention is a tradeoff: encrypted verification material accompanies later same-origin requests during that remainder and could appear in Cookie/header logging. HttpOnly does not protect platform logs; compromise of the operational encryption key could reveal captured ciphertext. No such key is created by these tests. Existing [logging gate](LOGGING-GATE.md) must still cover Cookie headers, callback URLs and platform/error traces; absence of app logging is insufficient evidence.

**Historical Cycle46 finding, superseded by the gated Cycle49 implementation:** latest-identity session response ordering was not satisfied. A success response prepared for active identity A, held until active B completes, replaces the shared session cookie with A when applied last. Both sessions remain independently valid server-side. This candidate fixes attempt deletion only. The executable fixture deliberately asserts that hazardous A-after-B result as a release-blocker reproduction, not a safe acceptance condition. The production source release gate stays false, with no real Google flow or remote changes. See [independent QA](QA-OAUTH-LATE-RESPONSE.md).

At Cycle46, the proposed next step was to choose and validate a server-side coordination protocol. One candidate used a browser coordination generation, atomically recorded the verified result for that generation, and finalized through a same-origin CSRF-protected command rather than issuing the session directly in the provider callback. Every authenticated request would need to reject sessions from an obsolete generation. A finalization CAS alone was insufficient: a response authorized before B could still arrive after B. Generation validation could fail closed on stale A but leave the browser signed out; recovery and the user's intended identity required explicit acceptance tests. A stable anonymous coordination cookie needed fixation, rotation, stolen-cookie and multi-device review and could not become a reusable authentication credential. This was a requirement for reviewed state/schema design, not permission to flip the gate.

The investigation also considered serializing identity transitions using server coordination and acknowledgment, while preventing delayed responses, lost acknowledgments and timeouts from reopening the race. Browser-only locks/BroadcastChannel, per-attempt cookie names, or JavaScript ignoring a stale body could not alone stop the browser applying a shared session Set-Cookie header. Required evidence included controlled reverse header application, different active identities, concurrent tabs, replay/expiry, logout, fail-closed handling and recovery. Actual browser/Google transport remained separate from this local fixture.

## Distinct legacy pending-only pilot exception

The normal `OAUTH_HTTP_RELEASE_ENABLED=false` remains unchanged. Complete Google configuration alone opens no route. The explicit pilot integration additionally requires the private, strictly parsed `OAUTH_PENDING_PILOT` JSON policy with `allowedEmail` and `expiresAtMs`; the deadline must be future, at most24hours away, and an integer epoch millisecond value. Do not commit the selected identity or operational policy. Invalid, missing or expired policy closes the pilot.

This legacy path is separate from ordinary self-registration. It serves `/api/auth/pilot` and a same-origin external script, then permits only bootstrap, `command?action=pending-registration`, the pilot's bodyless register call and registration-purpose callback. It collects no participation years and uses the legacy `|pending-registration` sealed audience. Register returns private no-store JSON containing the Google authorization URL and the existing sealed attempt Cookie. The browser navigates explicitly; it does not try to read the Location of an opaque manual redirect. The callback performs actual Google JWT verification, then exact email equality and a fresh deadline check immediately before the existing pending receipt store. Other identities are not persisted. It never falls back to ordinary login/self-registration, activates an account, creates a session, grants an operator role or enables private/posting routes. Callback outcomes are only `/api/auth/pilot#received` or `#unavailable`, without identity/token details. As with the ordinary callback, it never writes/deletes the attempt cookie.

This is consent to save the verified school email/subject privately for a pending application, not ordinary registration, enrollment approval or posting permission. Its historical review/approval preparation is not a mandatory stage of the adopted ordinary registration policy. Removing the private policy closes the pilot; it does not erase a deliberately accepted pending account. Existing protected retention/withdrawal procedures govern stored records. UI and responses do not embed the selected email. Actual OAuth/logging and operational production release requirements continue to apply. Local synthetic JOSE/browser results do not prove real Google consent-screen configuration or acceptance of an actual school identity.

Pilot routing follow-up: `/api/auth/pilot` and its external JS run inside the existing `/api/*` worker-first assets rule, before the generic auth handler. A local actual-production-entry browser check loads the configured static asset SPA fallback, then the pilot, and completes after a pre-existing context/bootstrap409; command issuance still validates that context. Late canonical GET callbacks after policy expiry/removal clean-redirect without DB/provider access. Other disabled factory and general route contracts remain closed.

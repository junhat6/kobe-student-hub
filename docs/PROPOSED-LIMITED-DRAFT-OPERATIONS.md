# 限定下書きの本番準備案（未実行）

対象は `kobe-student-hub-production` に接続された専用D1と同Workerの限定設定。Issue #4 の在籍判断・本人権限・私的データを扱う。これは実行手順の提案であり、現時点の本番DBのテーブル・移行履歴・申請行を確認した結果ではない。実データのSELECTは以前拒否されているため再試行していない。migration番号、実行コマンド、対象account IDや実日時は未確定であり、この文書だけで実行しない。

## スキーマ案

既存の local fixture `tests/fixtures/limited-draft-grants.sql` を本番向けmigration候補としてレビューし、新規の一行限定テーブル `limited_draft_grants` を追加する。`singleton=1` のPRIMARY KEY/CHECKで同時に最大1行、`account_id` は既存 `private_accounts(id)` を参照し一意、`account_epoch`、`expires_at_ms`、`revoked_at_ms` を保持する。既存アカウントや下書きを変更せず、grant行も作らない。既存テーブルとの名前衝突、D1の時刻・トランザクション・外部キー動作、migration番号・ledger整合を確認し、リハーサルと独立QA後に別の実行単位にする。重複や不整合を無条件の `IF NOT EXISTS` で隠さない。

## 初期許可案

1. 権限のある本人以外の運営者が在籍根拠、対象、承認範囲、失効時刻を非公開で確定する。学校メールだけを在籍承認とみなさない。既存の申請受付画面はDB行や在籍承認の独立証明ではない。
2. 既存接続と対象DB・現行migration・対象のpending状態・epochを、認められた方法と最小範囲で確認する。以前拒否された本番DB照会は別途適切な承認なしに実行しない。別のAPIで回避しない。
3. 現在の `AdmissionStore` は有効な運営者セッションと別アカウントへの操作を要し、初期operatorの付与も未実装。初期運営者の選定、役割付与・本人のpending→active移行、監査記録の設計と具体的な認可を別途決定する。手動で直接UPDATEして監査・検証を迂回しない。active移行は既存トリガーでepochを進めるので、移行後の値を確認する。
4. 制御された操作で、そのactive accountの最新epochと1件の期限を条件付きでgrantに登録する。入力はサーバー管理の値だけとし、対象状態・epoch・空きslot・期限を同一DB操作で確認する。期限は現行parserの24時間以内。既存の未取消grantを上書きしない。状態不一致、複数候補、既存row、結果不明は停止して照合し、再実行を前提にしない。
5. 限定Workerの非公開設定には、同一account ID・同一epoch・同一期限のみを設定する。現在の実装はDB grantと設定の双方が一致した時だけ動く。実際の設定と配備は別操作として、対象・内容・影響を確認した後に行う。一般ログイン・公開・他人への権限は含まない。

## 取消・再発行案

取消の正本はD1のgrant。対象ID・期待epoch・未取消状態を条件として `revoked_at_ms` をDB時刻で設定し、1行更新が確定してから取消完了とする。DB内で取消が先に確定した後のsession発行とprivate draft SQLは拒否される。既にDBで確定済みの操作は遡及しない。設定の削除だけではbind済み要求の取消を保証しない。取消結果不明なら状態を確認するまで再実行・成功報告をしない。

再発行は独立した明示判断とする。期限切れ・取消済みであることと対象/epochを確認し、古いsessionの復活を避けるため、実装済みのaccount status/epoch失効手順との整合を検証する。単に `revoked_at_ms=NULL` として旧grantを再使用しない。期限切れで元sessionが失効済みでも、ブラウザ内の未保存内容・保持済み下書きは自動消去されない。保持・本人の削除と復旧は別の運用判断であり、取消時に勝手に削除しない。

## 実行前の確認と影響

- 対象: 指定の本番Worker・本番D1・本人1件のみ。OAuth client・既存鍵は再利用し、新しいoperatorやsecretを暗黙に作らない。
- 操作の単位: (a) schema追加、(b) 独立の在籍承認と初期operator信頼連鎖、(c) 1件の期限付きgrant、(d) Worker限定設定・配備、(e) 実本人の限定試験、(f) DB取消と失効確認。それぞれ対象・影響・権限・結果不明時の扱いを確定する。
- 影響: schema追加は新規テーブルとmigration ledger、承認は本人のaccount status/epochと監査、grantは1行、配備はWorkerの版と限定設定を変える。期限・取消時はその後の認証/私的下書き操作を拒否する。一般公開や投稿の有効化は対象外。
- リスク: DB時刻とruntime時刻のずれ、取消と同時進行中の処理、初期operatorの信頼根拠、ログ・個人情報の扱い、DB結果不明、旧session復活、実D1とlocalの差異。時刻・実行順序を実D1で検証する必要があるが、現在その照会・変更は行わない。
- 配備不能時は限定経路を閉じ、既存データを削除せず、設定・grantの実状態を確認してから復旧する。DBをリセットしない。識別子・メール・鍵・実SQL結果は公開PRや通常ログに含めない。

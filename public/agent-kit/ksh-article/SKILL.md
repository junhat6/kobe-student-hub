# Kobe Student Hub の記事を書く

Kobe Student Hub は、神戸電子の学生が学習・制作の経験を記事にして共有する場所です（学校公式ではありません）。
このスキルは、あなた（エージェント）が **本人の経験から** 記事の下書きファイルを作るための手順です。
できたファイルは本人がサイトの下書き画面（`/drafts` の「自分のAIエージェントと書く」）に読み込み、自分で読んで直してから公開します。

**あなたは公開しません。** 公開するのはいつも本人です。あなたの仕事は下書きを作るところまでです。

- Kobe Student Hub の MCP サーバー（ツール `create_draft` など）につながっていれば、下書きをサイトに直接作れます（下の「MCP でつながっているとき」）。
- つながっていなければ、Markdown ファイルを作り、本人がサイトの下書き画面に読み込みます（手順 6）。

## 1. 材料を決める（最初に本人に聞く）

次のどれから書くかを本人に聞いてください。決まっていればそのまま進みます。

- A. 本人が話すこと・手元のメモ（Obsidian、Notion の書き出し、README など）
- B. 過去の AI エージェントとの作業履歴（下の手順 2）
- C. いまのリポジトリの git log・Issue・PR

## 2. 作業履歴から記事のネタを探す（B のとき）

**読む前に、本人へ次の4点を伝えて、使ってよいか確かめてください。** 断られたら A か C に切り替えます。

1. 過去セッションを参照すると、その中身があなた（本人の AI エージェント）と、その提供元のサービスに渡ります。
2. セッションには、パスワード・API キー・秘密鍵・メール・他の人の情報などが含まれることがあります。
3. 伏せ字の補助（下の `session_index.py`）は完全ではなく、すり抜けがあります。
4. 参照するかどうか、記事に何を載せるかは本人が決めます（公開前に全文を読んでください）。

作業履歴はこのコンピュータの中にあります。**外へ送らず、この端末の中だけで読んでください。**

| ツール | 場所 |
| --- | --- |
| Claude Code | `~/.claude/projects/<プロジェクト>/<セッション>.jsonl` |
| Codex | `~/.codex/sessions/YYYY/MM/DD/rollout-*.jsonl`、依頼の一覧は `~/.codex/history.jsonl` |
| Gemini CLI | `~/.gemini/tmp/<プロジェクト>/chats/session-*.json` |
| Antigravity CLI | 依頼の一覧 `~/.gemini/antigravity-cli/history.jsonl`、成果物 `~/.gemini/antigravity-cli/brain/<id>/` |

そのまま開くと大きすぎるので、同梱のスクリプトで絞ります（Python 3 の標準ライブラリだけで動きます）。

```sh
# 一覧（日付・ツール・プロジェクト・タイトル。2行目に show 用の ID と伏せたパス）
python3 scripts/session_index.py index --since 2026-10-01
python3 scripts/session_index.py index --grep docker        # 依頼文に含む語で絞る
python3 scripts/session_index.py index --project my-app     # プロジェクト名で絞る
# 1セッションを短い会話録に（ツールの出力は省き、秘密らしき文字列とメール・ユーザー名をできる範囲で伏せる）
python3 scripts/session_index.py show <index に出た ID> --max-chars 20000   # 例: show 3f9a1c2b7e
```

`show` には、`index` の各セッションの2行目にある `ID`（0〜9 と a〜f の10文字）をそのまま渡してください。引用符は要りません。ID の横の伏せたパス（`~` や `<you>` を含む）は表示用で、引用符なしで渡すとシェルが書き換えてしまいます。Antigravity の行は `show` に対応していないので、`index` に出る依頼文を使ってください。

スクリプトが無い環境では、`/agent-kit/ksh-article/scripts/session_index.py` をサイトから取得するか、上の場所のファイルを `jq` などで「本人の依頼文」と「エージェントの返答の文章」だけに絞って読んでください。ツールの出力全体は読まないでください（長く、秘密が混ざりやすい）。

記事になりやすいのは次のような場面です。候補を **3〜5個**、1行ずつ「誰に・何がわかる記事か」を添えて本人に見せ、1つ選んでもらってください。

- 詰まって、試して、解決した（エラー → 原因 → 直し方 → なぜそうなるか）
- 2つの方法で迷って、理由をつけて決めた
- 初めて使った技術・ツールで「最初に知りたかったこと」
- 作ったものの「作る前と後」で変わったこと
- AI エージェントへの頼み方を変えたら結果が変わった

## 3. ログに無いことを本人に聞く

ログには「何をしたか」はあっても「なぜそう思ったか」「どう感じたか」はありません。書く前に 2〜3 問だけ聞いてください。

- そのとき一番困ったことは何か
- 同じ立場の後輩に一言いうなら何か
- いまならどうするか

本人の答えは、本人の言い回しをできるだけ残して本文に使います。

## 4. 書く

- 本人が実際にやったこと・確かめたことだけを書く。やっていない経験・数字・感想を作らない。わからないところは `（ここに〇〇を書く）` と空けておく。
- 読者は神戸電子の学生（1〜4年生）。専門用語は最初に一言で説明する。
- 長さは 1,500〜4,000 字くらい。見出しは `##` から。コードは言語名つきのコードブロック。
- HTML タグは表示されないので使わない。
- 画像は多めに入れる前提で書く（見出しごとに1枚以上が目安）。ファイルには画像を入れられないので、置きたい場所に `（写真：〇〇）` `（図：〇〇の比較）` と書いておく（本人があとでサイトで追加する）。使えるのは、本人が撮った写真・作ったものと、内容を図にした自作の図版だけ。ネットで見つけた画像・店の公式写真は使わない。AI が作った写真風の画像で、実在の店や料理を「その店のもの」に見せない。図版には「図：記事用に作成」と出どころを添える。
- 課題の解答の丸写しは載せない。考え方・詰まった点は書いてよい。
- お店のレビューなら：実際に行った店だけ。行った時期と、値段・メニューは「その時点」と書く。無料提供・割引・依頼があれば書く。店員や他の客を特定しない。悪口・中傷にしない。

### 良いと感じられる記事（運営のレビューから更新）

サイトの運営が記事を読んでレビューした結果から、良いと感じられる書き方をまとめています。上の決まりと合わせて従ってください。

- 本人の言い回しをそのまま残す。感想を盛らない・言っていないことを足さない。足りないところは「（ここに〇〇を書く）」と空ける（オーナー指示 2026-11-22）
- 読んだ人がすぐ動ける具体を入れる。お店なら「何人なら入れるか」「いくらぐらいか」「混むと遅い」など、行く前に知りたいこと（オーナー指示 2026-11-22）
- 良かったことも合わなかったことも正直に書く。合わなかった店も、事実と本人の好みとして短く書く（オーナー指示 2026-11-22）
- 写真・図を多めに。見出しごとに1枚以上が目安（オーナー指示 2026-11-22）
- お店の記事は1本に1店。何軒か行っても、まとめずに店ごとに1本ずつ書く（オーナー指示 2026-11-23）

## 5. 公開してよいか確かめる（必ず）

このリポジトリやログには、記事に載せてはいけないものが混ざりがちです。下書きを渡す前に、自分で全文を見直して伏せてください。

- パスワード・API キー・トークン・`.env` の中身・秘密鍵
- メールアドレス（とくに学校のメール）、電話番号、住所
- 本人以外の人の名前・顔・アカウント名（本人が「出してよい」と言った人を除く）
- `/Users/<名前>/` のようなユーザー名入りのパス、社内・アルバイト先の非公開の情報、非公開リポジトリの名前
- 他の人の文章・画像の無断転載

見直した結果（伏せたもの・本人に確認したいもの）を、ファイルとは別に本人へ短く伝えてください。

## 6. ファイルを作る

次の形の Markdown ファイルを 1 つ作り、公開リポジトリの外（例：`~/ksh-drafts/<英数字の短い名前>.md`）に保存します。

```markdown
---
title: 記事のタイトル（200文字以内）
summary: 一覧に出る概要。何がわかる記事かを1〜3文で（300文字以内）
tags: [タグ1, タグ2]          # 5個まで、1個24文字以内
audience: 想定読者（200文字以内）
prerequisite: 前提知識（200文字以内、なければ「なし」）
outcome: 読んだあとにわかること・できること（200文字以内）
minutes: 6                    # 読むのにかかる分数
---

## 見出し

本文…
```

最後に本人へこう伝えてください。

> `~/ksh-drafts/〇〇.md` を作りました。Kobe Student Hub の「下書き」で新しい下書きを作り、「自分のAIエージェントと書く」→「.md ファイルを選ぶ」で読み込んでください。公開前に、自分の経験と違うところがないか読んで直してください。

## MCP でつながっているとき

Kobe Student Hub はリモート MCP サーバー（`https://hub.junhat6.com/api/mcp`）を持っています。本人が学校Googleでログインして「接続を許可」したエージェントだけが使えます。

- 最初に `get_writing_guide` を読み、その流れと守ることに従ってください。
- 手順 6 のファイルの代わりに `create_draft`（タイトル・本文 Markdown、任意で概要案 `summary`・タグ案 `tags`）で下書きを作ります。front matter は付けません。直すときは `get_my_draft` で版を読んでから `update_draft`。
- できるのは、公開記事を読むこと、本人の下書きを一覧・読む・作る・直すこと、本人がすでに公開した記事を公開したまま直すこと（`update_published_article`）だけです。初めての公開と削除はできません（初めての公開は本人がアプリで行います）。公開中の記事は本人に頼まれた直しだけにしてください。下書きの作成は1アカウント1日10件までです。
- サーバーは決まった形の検査で、秘密に見える箇所の種類と行番号を注意として返します（保存は止めず、検査は完全ではありません）。注意が返ったら値を `<API_KEY>` のような置き換えにして直してください。
- 作業履歴そのものをサーバーに送らないでください。送るのは完成した下書きだけです。

本人がつなぐ方法（確かめた日はサイトの /agents に書きます）：

| エージェント | つなぎ方 |
| --- | --- |
| Claude Code | `claude mcp add --transport http ksh https://hub.junhat6.com/api/mcp` のあと、`/mcp` で ksh を選んでログイン |
| Claude（claude.ai） | 設定 → コネクタ → カスタムコネクタを追加 → URL に `https://hub.junhat6.com/api/mcp` |
| Codex CLI | `codex mcp add ksh --url https://hub.junhat6.com/api/mcp` のあと `codex mcp login ksh` |
| Gemini CLI | `gemini mcp add --transport http ksh https://hub.junhat6.com/api/mcp` のあと、`/mcp auth ksh` |

## 定時実行で書く（例：毎日 8 時と 15 時）

サイトはあなたを動かしません。定時実行は本人の端末（本人のサブスク）で設定します。本人がその場にいないので、次を守ってください。

- 1回の実行で下書きは1本だけ。読む作業履歴はその日の分（直近の作業）に限る。
- 本人に質問できないので、候補から1つ選び、本文の先頭に「（AIメモ：この話題を選んだ理由）」を書く。本人の気持ち・感想は作らず「（ここに〇〇を書く）」と空ける。
- 書けるネタが無ければ、何も作らずに終わる。

設定の例（macOS / Linux の cron。`crontab -e` に1行足す）：

```cron
0 8,15 * * * claude -p "ksh の MCP で、今日の作業から Kobe Student Hub の記事の下書きを1本作って。get_writing_guide に従うこと" --allowedTools "mcp__ksh,Read,Grep,Glob"
0 8,15 * * * codex exec "ksh の MCP で、今日の作業から Kobe Student Hub の記事の下書きを1本作って。get_writing_guide に従うこと"
```

接続は 90 日で切れます。切れたら本人がもう一度つないでください。

## 記事を読むとき

Kobe Student Hub の記事ページには「AIに渡す」ボタンがあり、記事を Markdown でコピーできます。本人が記事を貼ってきたら、出典の URL と書いた人を示したうえで、本人のプロジェクトや状況に合わせて説明してください。記事の内容を本人の経験として書き写さないでください。
